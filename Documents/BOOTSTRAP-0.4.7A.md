# GrinSight 0.4.7A · автономный старт

Локальная опытная версия для Windows x64. База — GrinSight 0.4.6, Git `be41231cd7ab73f158f8219e3fc44d1c3fe781f6`. Для воспроизводимости сохранена отдельная ветка. В рабочем дереве после этой версии обнаружены отличия в UI, доставке, платёжном коде и упаковке. Изменений в дереве проверки цепи относительно выбранной базы при сравнении не обнаружено. Все результаты ниже относятся к этой ветке.

## Что меняется для владельца кошелька

Актуальный вариант запуска, формат пары для передачи и проверка на другом Windows-компьютере описаны в [решении о локальной точке и GSHP1](ADR-LOCAL-CHECKPOINT.md). Ниже зафиксированы поведение и результаты предыдущего, полностью автономного варианта 0.4.7A. [Исследования полной переносимой проверки](BOOTSTRAP-PORTABLE-PROOF.md) продолжаются отдельно.

На чистом устройстве приложение берёт genesis из правил выбранной сети, последовательно получает заголовки у обычных Grin-пиров, проверяет их и строит собственную точку для получения PIBD. Поставщик доказательств и выпуск новой точки автором для этого пути не требуются. По завершении состояние и поиск собственных выходов обрабатываются штатными компонентами 0.4.6. Синхронизация не запрашивает у поставщика seed, адреса или список интересующих кошелёк выходов.

При обновлении на месте файлы кошелька и старый `own-point.json` сохраняются. На первом открытии 0.4.7A траты времени и диска включают построение собственного проверенного префикса. Локальные точки 0.4.6 сами наследуют доверие своему начальному заголовку. Передавать это доверие новой версии при миграции было бы ошибкой. После повторного открытия 0.4.7A перечитывает и проверяет журнал с диска и догружает заголовки по необходимости. Детали синхронизации показывают способ проверки, локальную точку, работу проверенной вершины и отдельно состояние её выбора. Действие перепроверки запускает повторное открытие, при следующей разблокировке проверка читает локальную историю от genesis. Исходное приложение 0.4.6 и его опубликованные файлы остаются доступны для сравнения.

## Модель доверия

| Утверждение | Основание | Что может остаться неизвестным |
|---|---|---|
| Это исторически допустимая последовательность заголовков данной сети | Точное равенство genesis, ссылки, версия, PoW, требуемая и накопленная работа, время, смена DAA, header PMMR на каждом шаге | Все транзакции от genesis не исполнялись |
| Работы на новой ветви больше, чем на проверяемой локальной | Накопленная работа двух проверенных префиксов. Переход на глубокую ветвь требует строго большего значения | Изолированному клиенту могут вообще не показать лучшую ветвь |
| Получено состояние на выбранной ветви | Существующая проверка PIBD, корней и тел. До полной сборки архив остаётся неполным | Одна корректная ветвь не устанавливает глобальную свежесть |
| Выбор вершины подтверждён политикой кошелька | Отдельные условия Accept, свежести времени и независимости операторов | Отсутствие доступных независимых свидетелей сохраняет неопределённость |
| Выход принадлежит кошельку | Проверенные данные выхода и локальная проверка с ключами пользователя | Стадия доставки Slatepack и состояние платежа устанавливаются отдельно |

Предположения — совместимый консенсус и программа, исправная криптография Grin, возможность получить достаточные ресурсы и для актуальности добраться до честных источников. При полном eclipse, подменённых DNS, отсутствии известных пиров или сговоре нельзя вывести свежесть только из корректного PoW или количества сокетов. Правильный старый префикс не становится текущим автоматически. На диске хранится доказательная база, поэтому замена единственного JSON не позволяет придумать работу. Откат целого устройства к старой согласованной копии способен скрыть недавнее состояние устройства. Связывать такой префикс с «текущим балансом» без повторной проверки нельзя.

## Путь данных

1. В 0.4.6 начальный артефакт выбирался до создания `HeaderChain`. Проверка формы точки и продвижение через `record_at` не проверяли всю историю перед ней. В 0.4.7A для Mainnet и Floonet исходными данными служат только genesis и проверяемые заголовки.
2. `Source/chain/headers/src/genesis.rs` держит скользящий контекст DAA, вершину и пики. `Source/chain/fly-chain/src/bootstrap.rs` получает ограниченные страницы GetHeaders, хранит проверенный префикс и ограниченный хвост до передачи штатному движку. Транспорт использует тот же выбор маршрута кошелька. В новом протоколе ноды или PR #3963 необходимости нет.
3. В фазе последующего сопровождения `record_at` строит точки на доступной архивной сетке протокола. На Mainnet архив привязан к интервалу в 720 блоков и порогу состояния Grin. Такая точка пригодна для штатного PIBD. Хранятся до трёх вращающихся снимков в каждом поколении. Файл снимка — производная от перепроверяемого журнала. Переключение глубоких ветвей использует отдельное поколение и сохранённую границу работы. Хранилище проверенного префикса растёт с длиной цепи. Во время смены ветви может понадобиться место для двух поколений.
4. За выбор ветви и передачу состояния отвечают `fly-chain/src/node.rs` и `feed.rs`; host получает результаты через штатный IPC. Проверки времени и независимых источников остаются в `Source/chain/tips` и `fly-chain/src/accept.rs`. Доступ к валидным заголовкам и наличие выбранной вершины имеют разные критерии, в том числе для автоматической финализации платежа.
5. Необязательный провайдер поставляет кандидаты GSHP1. Транспорт, зеркало, контрольная сумма и успешная проверка формата не дают права заменить genesis доверенной удалённой точкой. Для формата 0.4.6 не установлена требуемая вероятность ложного принятия. Обоснование по методам, стоимость измеренных операций и инструкция оператора приведены в [BOOTSTRAP-PROOFS.md](BOOTSTRAP-PROOFS.md).

## Доступность без автора через несколько лет

При доступности совместимой сети с хотя бы одним достижимым честным пиром, который отдаёт нужные заголовки и состояние, сеть может предоставить всю историю без новой публикации автора. DNS-сиды или заранее известный адрес нужны для обнаружения первого пира. Полное исчезновение встроенных HTTPS-свидетелей и независимого времени оставляет подтверждение свежести недоступным. Ручная отправка и автоматическое подписание имеют разные условия в 0.4.6, их точная граница разобрана отдельно. Совпадение ответов нескольких случайных P2P-пиров не доказывает независимости. Поэтому общее требование «только P2P, актуальная вершина и полный подтверждённый платёжный путь при исчезновении всех остальных операторов» остаётся открытым.

Для следующего решения есть два проверяемых варианта. Можно сохранить нынешнюю политику подтверждения и разработать обновляемые, независимо обнаруживаемые источники аттестации с явно проверяемой независимостью. Тогда условия свежести остаются дополнительным предположением. Либо можно определить отдельный уровень доверия «лучшая локально наблюдаемая цепь» с явной моделью изоляции и отдельным правилом разрешённых операций. Такой выбор меняет гарантии платежей и требует отдельного решения. Ни один вариант не даёт криптографического доказательства глобальной свежести из одного старого совместимого префикса.

## Производительность и воспроизведение

На одном локальном Windows x64-хосте проверка 1 648 750 байт заголовков без сети заняла по медиане 157,511 мс у 0.4.6 и 154,842 мс у 0.4.7A. Процессорное время в обоих случаях 140,625 мс. Пик рабочего набора 6 008 832 и 5 636 096 байт соответственно. Эти прогоны измеряют верификатор, а не время первого запуска кошелька. Методика, сырые ряды, SHA-256 и команды находятся в [отчёте верификатора](../Source/chain/headers/BOOTSTRAP-0.4.7A.md).

Дополнительно измерено полное дерево процессов Windows на локальной цепи. Восстановление и платёж заняли 14,328 с, CPU дерева 3,547 с и пик выделенной памяти 37 822 464 байта. Переход на более тяжёлую ветвь ниже архива занял 19,524 с, CPU 4,781 с и 11 218 944 байта. [Методика Job Object и исходные измерения](BOOTSTRAP-0.4.7A-JOB-BENCH.md).

Сохранённый отчёт 26.11 указывает 1 711 006 919 байт для 4 123 322 заголовков Mainnet в кадрированном файле. Это ориентир масштаба первого старта; реальный трафик с повторами, служебными сообщениями, PIBD и восстановлением профиля будет другим. Для нового кошелька, восстановления старого seed, долгого отсутствия, Android, глубокого реорга на реальном размере цепи и полного последовательного старта отсутствует парный замер 0.4.6 и 0.4.7A по времени, трафику, CPU, RAM и объёму диска. Компактный автономный старт не имеет такого замера, пока не определена принимаемая конструкция. Для полной приёмки нужны публичный файл истории с известным digest или разрешённый стенд обычных нод, одинаковые аппаратные условия и отдельный Android-стенд.

Из `Source/chain/headers` запустить `cargo test --release --locked --offline`. Из `Source/chain/fly-chain` — `cargo test --locked --offline --features test-net`. Из `Source/ui/app` — `cargo test --release --locked --offline --lib`. Для автономного воспроизведения подготовить реестр зависимостей 0.4.6 (Cargo vendor) и Rust/MSVC соответствующей версии. Зависимости Grin из репозитория входят в архив исходников. Заново использовать локальные хранилища зависимостей и путь CARGO_TARGET_DIR разрешено. Архив не содержит рабочие профили или необработанные данные цепи.

На хосте разработки готовые каталоги реестров лежали в `core-v0.2/vendor-crates` и `core-v0.2/ui/vendor-crates`. При воспроизведении их можно подключить соответственно как `Source/vendor-crates` и `Source/ui/vendor-crates` в распакованных исходниках. Первый нужен для цепи/инструментов, второй — для окна. Lock-файлы входят в поставку. Глобальные кэши Cargo, цепь и пользовательские профили в архив исходников не входят. В полном исходном дереве есть публичные тестовые TLS-ключи localhost, входившие и в 0.4.6. Они используются только локальным стендом.

Для текущего варианта Windows собрать `fly-chain`, `fly-paycore-host` и `fly-ui` командой `cargo build --release --locked --offline --bin <имя>` из каталогов `chain/fly-chain`, `paycore/host` и `ui/app` соответственно. Запустить из `Source` с Windows PowerShell:

~~~powershell
.\run-autonomous-portable.ps1 -BaseExe <portable-0.4.6.exe> -WindowExe <fly-ui.exe> -ChainExe <fly-chain.exe> -HostExe <fly-paycore-host.exe> -OutputDir <новая-папка>
.\test-autonomous-portable.ps1 -Executable <portable-0.4.7A.exe> -TestRoot <временная-папка>
~~~

Упаковка проверяет закреплённый SHA-256 оригинального portable и берёт из него компоненты транспорта. Проверка кандидата использует отдельные временные профили. SHA-256 артефактов доставки находится рядом с EXE.
