# Предложение: доказательства принадлежности заголовков (Header MMR proofs) в P2P-протоколе Grin

Статус: черновик для реализации в форках Grin (Rust) и Grin++ (C++), тестирования и последующего предложения разработчикам Grin. Дата: 2026-11-10.

Коротко: узел по запросу отдаёт полный заголовок на высоте H и путь Меркла от него до `prev_root` выбранного якорного заголовка. Консенсус не меняется: `prev_root` уже проверяется каждой полной нодой. Это даёт лёгкому клиенту произвольный проверяемый доступ к истории и делает возможной выборочную (в духе FlyClient) проверку работы цепочки за мегабайты вместо ~1,9 ГБ полного синка заголовков.

---

## 1. Зачем

Лёгкий клиент Unity доказуемо восстанавливает состояние UTXO от архивной высоты до вершины (см. `PLAN_VERIFIED_LIGHT_MODE_RU.md`). Но доверие к самой цепочке заголовков сейчас опирается либо на встроенный чекпоинт, сверенный с публичными источниками, либо на полный синк заголовков с генезиса. Цена полного синка на mainnet:

- ~4,1 млн заголовков, ≈ 1,9 ГБ трафика (расчёт: ~455 байт на заголовок Cuckatoo32);
- ~27 мин с близкого быстрого узла при ≤ 300 запросах/мин; 3+ часа с далёкого публичного узла;
- узлы банят за > 500 сообщений/мин; узел, к которому уже подключена своя нода пользователя, не принимает второе соединение с того же IP.

Для телефона это неприемлемо как путь по умолчанию. Проверка случайной выборки заголовков с доказательствами принадлежности устраняет большую часть этой цены.

## 2. Что уже есть в консенсусе (ничего менять не нужно)

Ссылки — ветка `staging` основного репозитория Grin, коммит `83ff9af` (2026-10-15, версия 5.5.2).

- **`prev_root` в каждом заголовке** — корень MMR всех предыдущих заголовков (высоты 0..H−1). Полная нода проверяет его при приёме заголовка: `chain/src/txhashset/txhashset.rs`, `HeaderExtension::validate_root` (ошибка `InvalidRoot`). Значит, корень защищён PoW самого заголовка.
- **Лист MMR заголовков** = `H(be64(pos) || упакованные nonces PoW-доказательства)` — та же хеш-форма заголовка, что и `header.hash()`; через PoW-доказательство (ключи siphash выводятся из pre-pow) лист связывает все поля заголовка. Это уже воспроизведено и проверено в клиенте Unity: `header-sync/src/mmr.rs` (`header_leaf_hash`, родитель, «мешок» пиков), сверка `prev_root` для каждого скачанного заголовка (`HEADER_SYNC_MMR_CHECKED`).
- **Размер MMR, к которому относится `prev_root` заголовка H**: в нём H листьев, размер = `pmmr::insertion_to_pmmr_index(H)` (0-индексная позиция следующей вставки).
- **Структура доказательства** уже есть в ядре: `core/src/core/merkle_proof.rs` (`MerkleProof { mmr_size, path }`, `verify(root, element, node_pos)`).
- **После HF4 (высота 1 048 320 на mainnet; `header_version` = 5)** сложность считает WTEMA только по двум последним заголовкам (`consensus::next_wtema_difficulty`), вторичного PoW больше нет (`secondary_scaling` = 0). Метка времени заголовка строго больше предыдущей, поэтому сложность может расти не быстрее чем в 14400/14341 ≈ 1,0041 раза за блок (`WTEMA_HALF_LIFE` = 14 400 с, `BLOCK_TIME_SEC` = 60 с). Это сильно упрощает проверку правила сложности на выборке: для заголовка H нужны только H−1 и H−2.
- **До HF4**: DMA по окну 60 блоков и двойной PoW со `secondary_scaling` — проверка выборки дороже (окно 61 заголовок, ~28 КБ на точку).

## 3. Что уже есть в протоколе

- **PIBD** (`PIBD_HIST` 0x10, `PIBD_HIST_1` 0x40): сегменты UTXO/rangeproof/kernel с доказательствами против корней архивного заголовка.
- **PIHD** в `staging` (`p2p/src/msg.rs`: `GetHeaderSegment = 29`, `HeaderSegment = 30`; бит `PIHD_HIST = 0x80`, `p2p/src/types.rs`):
  - сегмент = 512 полных заголовков по индексу (`PIHD_HEADER_SEGMENT_HEIGHT = 9`), высоты `idx·512+1 … idx·512+512` — произвольный доступ к заголовкам по высоте, параллельная загрузка с многих узлов;
  - доказательств Меркла нет: сегменты проверяются цепочкой `prev_hash` и PoW;
  - сервер (`servers/src/common/adapters.rs`, `locate_header_segment`) **отвечает только пирам, которые сами объявили `PIHD_HIST`**, лимит 500 запросов/мин на адрес;
  - `PIHD_HIST` входит в `Capabilities::default()` в `staging`. На mainnet 2026-11-10 узлы `MW/Grin 5.5.2.c315228` объявляли `caps=0xdf` (с 0x80), например `103.98.150.38`, `103.98.149.6`.
- **Grin++, форк `DanilaGrinRus/GrinPlusPlus-BearTry-contrib` (`Main`, `ba8f237`)**: PIHD только клиент (`src/P2P/Sync/PihdClient.h`, отдача не реализована, `PIHD_HIST` не объявляется); MMR заголовков есть (`src/PMMR/HeaderMMRImpl.h`: `Root(lastHeight)`, `GetHashAt(index)`) — этого достаточно, чтобы строить доказательства.
- **Неизвестные типы сообщений** Rust-узел пропускает (`p2p/src/codec.rs`, `Message::Unknown`), но новые запросы всё равно следует слать только пирам с соответствующим битом.

Вывод: PIHD уже закрывает «параллельный синк заголовков с генезиса» (уровень 2 в плане). Не хватает только доказательства принадлежности — небольшого дополнения рядом с PIHD.

## 4. Предлагаемое расширение

### 4.1 Возможность

`HEADER_PROOF_HIST = 0x100` (следующий свободный бит в `Capabilities: u32`; согласовать с разработчиками Grin). Узел объявляет его, только если умеет отвечать на запросы ниже.

### 4.2 Сообщения

Номера — следующие свободные после PIHD (31/32; согласовать).

```
GetHeaderProofs (31)
  anchor: Hash          // хеш якорного заголовка A в основной цепочке узла
  count:  u16           // 1..=64
  heights: [u64; count] // каждая высота < A.height, по возрастанию, без повторов

HeaderProofs (32)
  anchor:   Hash
  mmr_size: u64         // = insertion_to_pmmr_index(A.height)
  count:    u16
  items: [count] {
    header: BlockHeader // полный заголовок (как в Headers)
    path_len: u8        // <= 64
    path: [Hash; path_len] // MerkleProof.path для листа header против A.prev_root
  }
```

- Доказательство строится против MMR размера `mmr_size` (исторического, не текущего): пути внутри поддерева + пики MMR этого размера, «мешок» как в `MerkleProof`. Хеши в MMR заголовков только дописываются и не обрезаются, поэтому исторический корень вычислим из текущего файла хешей. Нужна функция «доказательство для позиции `pos` при размере `size`» (в Rust — вариант `merkle_proof` для `ReadonlyPMMR::at(backend, size)`; в Grin++ — поверх `HeaderMMR::GetHashAt`).
- Узел отвечает, только если `anchor` лежит в его основной цепочке заголовков; иначе молчит (без бана), как PIBD при неизвестном архивном хеше.
- Детерминизм: при одинаковых `anchor` и `heights` ответ байт-в-байт одинаков у любой реализации — это главный межреализационный тест.

### 4.3 Размеры и лимиты

- Элемент ≈ 455 Б заголовок + ≤ 22·32 = 704 Б путь ≈ 1,2 КБ; ответ на 64 высоты ≈ 75 КБ (меньше `max_block_size`, лимит сообщения не нарушается).
- Лимит: общий счётчик с PIHD — не более 500 запросов/мин на адрес; запросы сверх лимита игнорируются без бана.
- Стоимость на узле: O(count · log n) чтений хешей из уже существующего файла + чтение заголовков по хешу. Дешевле PIBD-сегмента.

### 4.4 Проверка на клиенте

Для каждого элемента:
1. лист вычисляется из заголовка как `H(be64(pos) || nonces)` (`mmr.rs::header_leaf_hash`), `pos = insertion_to_pmmr_index(header.height)`;
2. путь сходится к `A.prev_root` при `mmr_size`;
3. PoW заголовка валиден для его сложности (`total_difficulty(h) − total_difficulty(h−1)`, для этого в запрос включается и h−1);
4. для проверки правила сложности после HF4 — тройки h−2, h−1, h: `prev_hash` связаны, сложность h равна `next_wtema_difficulty` по h−1, h−2.

Любое несоответствие — пир лжёт: отключить и не использовать.

## 5. Клиентский алгоритм (эскиз, требует анализа)

1. Получить кандидатов на вершину от ≥ k пиров из разных сетей; выбрать цепочку с наибольшей заявленной работой; последние N заголовков (например, 720) скачать и проверить полностью обычным синком — это якорь A и защищённый «хвост».
2. Выборка по работе: точки распределяются по накопленной работе от 0 до `A.total_difficulty`, плотнее к вершине (как в FlyClient). MMR Grin не взвешен по работе, поэтому высота для заданной работы находится двоичным поиском по `total_difficulty` заголовков с доказательствами (≈ log₂ n запросов на точку; запросы группируются по 64 высоты). Упрощённый вариант для оценки: сначала грубая карта работы по высотам с шагом 2^k, затем точки внутри интервалов.
3. Каждая точка проверяется по §4.4 (тройка заголовков после HF4).
4. История до HF4 (≤ 1 048 320): либо проверка окон по 61 заголовку, либо закрепление одним встроенным «историческим чекпоинтом» на высоте HF4 (он не меняется, его легко сверить с любыми источниками), а выборкой проверять только историю после HF4. Второй вариант практичнее.
5. Результат: якорь A, подтверждённый выборкой работы; дальше — обычный синк от A и доказуемое состояние UTXO (уже реализовано в Unity).

Оценка трафика (до замеров): тройка ≈ 3,6 КБ на точку + двоичный поиск ≈ 22 элемента по 1,2 КБ; при сотнях точек — порядка единиц–десятков МБ против ~1,9 ГБ.

## 6. Безопасность

**Консенсус.** Не меняется: новых правил валидности блоков и заголовков нет; данные (`prev_root`, MMR заголовков) уже консенсусные. Совместимость: новые сообщения шлются только пирам с битом `HEADER_PROOF_HIST`; старые узлы их не видят.

**Узел-отправитель.**
- Подделать доказательство невозможно без коллизии Blake2b. Узел может только не ответить или ответить мусором — клиент проверяет и уходит к другому пиру.
- DoS ограничен: ≤ 64 элемента на запрос, O(log n) чтений на элемент, лимит 500/мин.
- Приватность: заголовки публичны; запрос раскрывает только интересующие клиента высоты (как и сейчас при синке).

**Клиент (главная часть, требует формального анализа).**
1. Гарантия вероятностная: при честной работе большинства майнеров и хотя бы одном честном пире подделка цепочки обнаруживается с вероятностью, зависящей от числа точек. Параметры (число точек, доля «хвоста», распределение) надо вывести для Grin, а не переносить из статьи FlyClient: там MMR взвешен по работе, у Grin — нет.
2. Атака повышения сложности: подставная цепочка из малого числа дорогих блоков. После HF4 ограничена правилом WTEMA и строгим ростом меток времени (рост сложности ≤ ~0,41 % за блок) и проверяется на каждой точке тройкой заголовков. Это аргумент, а не доказательство — нужен анализ, включая ограничение будущих меток времени (по умолчанию 5 мин: `DEFAULT_FUTURE_TIME_LIMIT` = 300 с в Grin, `5 * BLOCK_TIME_SEC` в Grin++; в Grin настраивается `future_time_limit`, т. е. это политика узла, а не правило консенсуса).
3. Eclipse: если все пиры клиента у злоумышленника, он может не отдавать честную цепочку. Выборка не заменяет разнообразия пиров (разные /16, известные, но не подключённые узлы; соседние подсети считать одним источником).
4. До завершения анализа режим не должен быть единственной защитой средств: по умолчанию остаётся уровень 1 (встроенный чекпоинт + сверка), выборка — дополнительная проверка и замена полного синка в уровне 2.

**Хард-форк не нужен.** Вариант «как в статье» (MMR, внутренние узлы которого фиксируют накопленную работу) потребовал бы изменения консенсуса; плановых хард-форков в Grin больше нет, поэтому проект строится поверх существующего `prev_root`.

## 7. План реализации

### 7.1 Rust (форк `mimblewimble/grin`, от `staging`)
1. `p2p/src/types.rs`: бит `HEADER_PROOF_HIST`; `p2p/src/msg.rs`: типы 31/32, структуры, лимиты чтения (count ≤ 64, path_len ≤ 64), `max_msg_size`.
2. `core`: функция доказательства для произвольного размера MMR (`merkle_proof_at(size, pos)`), тесты против `MerkleProof::verify`.
3. `p2p/src/protocol.rs` + `servers/src/common/adapters.rs`: обработчик `GetHeaderProofs` (якорь в основной цепочке, высоты < A.height, общий лимит с PIHD), ответ `HeaderProofs`.
4. Тесты: случайные высоты против `prev_root` реальной цепочки (Floonet/mainnet фикстуры); граничные (высота 0, A.height−1, пики); отказ на чужом якоре; лимиты; fuzz парсера.

### 7.2 C++ (форк Grin++ BearTry)
1. `MessageTypes.h`: 31/32; `Capabilities.h`: бит; сериализация.
2. Доказательство поверх `HeaderMMR` (`GetHashAt`, пики для размера `insertion_to_pmmr_index(A.height)`).
3. Обработчик в `MessageProcessor.cpp` по образцу PIBD-ветки (точный хеш якоря, лимит, без бана при отказе).
4. Тесты: те же фикстуры, что у Rust.

### 7.3 Клиент Unity
1. `header-sync`: проверка `HeaderProofs` поверх `mmr.rs` (функции листа/родителя/пиков уже совпадают с Grin).
2. Режим `--sample-from-genesis`: якорь + хвост, выборка, двоичный поиск по работе, тройки WTEMA; вывод метрик (трафик, время, число точек).
3. Пока серверов нет — тест на локальной фикстуре: «сервер» отвечает из полной цепочки, сохранённой полным синком.

### 7.4 Межреализационная приёмка
- Rust- и C++-узел на одной цепочке дают **байт-в-байт одинаковые** `HeaderProofs` на одинаковые запросы (сотни случайных наборов высот).
- Клиент Unity принимает ответы обоих и отвергает испорченные (подмена заголовка, пути, размера, якоря).
- Mainnet: якорь, подтверждённый выборкой, совпадает с результатом полного синка с генезиса; замер трафика и времени против ~1,9 ГБ / ~27 мин.
- Floonet с обеими реализациями одновременно.

## 8. Открытые вопросы к разработчикам Grin

1. Номера сообщений и бит возможности: 31/32 и 0x100 свободны во всех ветках? Как координируется с другими расширениями?
2. Включать ли `HEADER_PROOF_HIST` в `Capabilities::default()` сразу или сначала за флагом конфигурации?
3. Отвечать ли PIHD/доказательствами пирам без соответствующего бита (сейчас PIHD-сервер отвечает только объявившим `PIHD_HIST`; лёгкому клиенту для получения ответа придётся объявлять бит)?
4. Нужен ли исторический чекпоинт на HF4 в самом протоколе/кошельках или это решение клиента?
5. Готовность сообщества рецензировать анализ безопасности выборки для Grin (WTEMA, метки времени).

Отличия реализаций, о которых стоит знать:
- Rust объявляет `HEADER_PROOF_HIST` в `Capabilities::default()`; Gplus добавляет бит в `ADVERTISED` (для ответа нужен только header MMR, PIBD-готовность не требуется).
- Лимит: Rust делит бюджет PIHD (500/мин на адрес); Gplus — поконнектный `AllowPibdRequest()`.
- Gplus перед ответом сверяют `Root(anchor.height-1) == anchor.prev_root` (самопроверка), при расхождении молчат.
- Неизвестный якорь, якорь не на основной цепочке, высоты не по возрастанию или ≥ высоты якоря — молчание без бана в обеих.
