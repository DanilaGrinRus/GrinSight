# Этап Э1: хранилище-журнал (`fly-paycore-store`)

Реализация раздела 5 спецификации платёжного ядра (ред. 0.3). Отдельный крейт, в репозиторий Fly не встроен. Ничего не знает о кошельке, slate и цепи: тела кадров для него — непрозрачные байты.

## Что сделано

- Журнал кадров: шифрование XChaCha20-Poly1305, цепочка hash, порядок «запись → `fsync` → применение».
- Открытие с проверкой каждого кадра; рваный хвост отбрасывается и срезается с диска.
- Страж хвоста: запись после устойчивого кадра, догон при открытии, обнаружение отката и переноса; пока не записан кадр восстановления, остальные записи отклоняются.
- Снимки и поколения файлов: снимок, новый файл журнала, затем кадр-переключатель в старом — точка фиксации. Хранятся два поколения.
- Один писатель: блокировка каталога.
- Квитанции `Receipt` и `Sealed` нельзя создать вне крейта. Верхний слой будет требовать `Sealed` для подписи и раскрытия, так что порядок «устойчиво → страж → действие» проверяет компилятор.

## Безопасность кода (раздел 15)

- `#![forbid(unsafe_code)]`; в рабочем коде нет `unwrap`, `expect`, `panic!`, индексации без проверки и непроверяемой арифметики — это запрещено линтами clippy на уровне `deny`, сборка с ними чистая.
- Разбор файла — через курсор с проверкой границ; предел размера проверяется до выделения памяти.
- Ключи и расшифрованные тела затираются при уничтожении; у `RootKey` нет `Debug` и `Clone`; ошибки несут только коды.
- Случайность — только генератор ОС, сбой — ошибка. Сравнение hash и MAC — за постоянное время.
- Имена файлов — из фиксированного алфавита; на Unix права 0600 / 0700.
- После сбоя записи хранилище отравлено до повторного открытия.

## Тесты

`cargo test` — 17 тестов, результаты в `test-results.txt`.

| Тест | Что проверяет |
|---|---|
| `crash_at_every_operation` | 3 968 прогонов: падение до и после каждой из 62 операций сценария × 16 вариантов судьбы несброшенных данных (потеряны, сохранены, обрезаны на разных байтах, нули, мусор) × судьба несброшенных изменений каталога. Журнал всегда открывается в состояние «после подтверждённых шагов» или «плюс шаг в полёте»; страж не даёт ложной тревоги и не отстаёт от подтверждённого кадра; запись продолжает работать |
| `corruption_of_every_byte` | три вида порчи каждого байта файла: 1 068 отказов, 276 случаев потери ровно последнего кадра; изменённое содержимое не возвращается никогда |
| `truncation_at_every_length` | обрезка на каждой длине: отказ или корректный префикс; страж сообщает о каждой потере закреплённого кадра |
| `random_damage_never_panics_or_forges` | 20 000 случайных повреждений (замена, вставка, удаление, дописывание): нет паник, возвращается только префикс записанного |
| `tail_guard_table`, `guard_across_generations` | все строки таблицы 5.7, откат через границу поколения, падение на каждой операции снимка |
| `model_trace_a5_guard_catch_up` | трасса A5 модели воспроизводится как обнаруженный откат |
| `failed_operation_poisons_until_reopen` | отказ записи, `fsync` и стража |
| остальные | ключ и идентичность, пределы, блокировка, отсутствие открытого текста и повторов nonce, реальные файлы |

**Проверка самих тестов.** Семь намеренных поломок кода (нет `fsync`; нет догона стража; страж до кадра; хвост не срезается; откат не помечается; запись при ожидающем восстановлении; нет `fsync` каталога перед переключением) — каждая роняет тесты.

## Уточнения к спецификации, выявленные при реализации

Для следующей редакции:
1. Рваным хвостом считается **любой** непроверяемый остаток файла (обрезанный кадр, нули, мусор), если после него не начинается ни один корректный кадр; иначе это повреждение. Ред. 0.3 говорила только о «некорректном последнем кадре».
2. При открытии страж догоняется до хвоста, поэтому после чистого открытия он покрывает и незакреплённые кадры.
3. Незавершённое первое создание (файл без корректного заголовка и без кадров) заменяется при повторном создании.
4. Свёртка устроена как смена поколения файла: кадр `Checkpoint` из 5.5 — это кадр-переключатель в старом файле; новый файл ссылается на снимок в аутентифицированном заголовке.
5. После обнаруженного отката хранилище принимает только кадр восстановления (в него верхний слой запишет новую ветку и блокировку операций).

## Чего нет

- Реализаций стража для Windows (DPAPI) и Android (Keystore) — здесь только интерфейс `Guard`; в тестах его заменяет модель и файл.
- Сборки и прогона на Windows и Android: всё проверено на Linux. На Windows нет `fsync` каталога — это учтено в коде, но не испытано.
- Испытаний настоящим отключением питания: падения моделируются.
- Теста блокировки двумя процессами (проверены два открытия в одном процессе) и fuzz-тестов через cargo-fuzz (вместо них — 20 000 случайных повреждений).
- Загрузки предыдущего снимка для отката цепи — это этап Э6.

## Дополнение 21.11: файловый страж (`FileGuard`)

Страж хвоста в одном файле **вне** каталога кошелька: 80 байт, значение под HMAC-SHA256 ключом, который передаёт вызывающий; запись через временный файл, `fsync` и переименование. Повреждённый файл — ошибка открытия, а не «стража нет». Только `std`, без `unsafe`.

Что он даёт: обнаружение отката или подмены каталога кошелька (старая копия, синхронизируемая папка), пока файл стража не откатили вместе с ним. Чего не даёт: защиты от отката всего диска или профиля и от клона устройства. Привязка ключа к устройству — дело платформенного слоя: на Windows ключ разворачивается DPAPI, на Android хранится в Keystore. **Этих обёрток здесь нет**, и собрать крейт под Windows и Android в этой среде не удалось (целевые наборы Rust недоступны).

Тест `file_guard_authenticates_and_detects_rollback_of_the_wallet_directory`: порча каждого байта, каждая длина обрезки, лишний байт, чужой ключ, брошенный временный файл, откат каталога кошелька к копии — `RolledBack`. Всего в крейте теперь 18 тестов.
