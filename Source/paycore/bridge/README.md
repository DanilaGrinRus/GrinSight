# Прокладка: подключение ядра к интерфейсу и внешним модулям (`fly-paycore-bridge`)

Один слой между платёжным ядром и всем, что вне его. Две стороны:

- **к интерфейсу** — `Bridge::call(запрос) -> ответ`: JSON-RPC 2.0, методы `paycore.*`. Транспорт любой; для Flutter сегодня — тот же `/rpc` локального сервиса, которым приложение уже пользуется;
- **к внешним модулям** — порты (`src/ports.rs`): четыре трейта, которые реализует хост.

```
Flutter (paycore_api.dart)
      │  JSON-RPC 2.0, методы paycore.*
      ▼
grinsight-service  ──►  Bridge::call        ◄── хост открывает Core сам:
      │                     │                    seed, ключ журнала, страж
      │                     ▼                    через JSON не проходят
      │                   Core (wallet)
      │                     ▲
      └── порты:            │ chain_advance / rollback / checkpoint
          Broadcaster  Clock  ChainView  SlateCodec   (ядро Fly, сеть, часы)
```

## Что не проходит через прокладку

Seed, ключи, контексты подписи, ключ журнала, ключ стража. Хост сам открывает `Core` и отдаёт его в `Bridge::new`. Факты цепи тоже идут не через JSON: слой цепи вызывает `bridge.core_mut().chain_advance(...)`.

## Порты

| Трейт | Кто реализует | Что делает |
|---|---|---|
| `Broadcaster` | сетевой слой | отправляет готовую транзакцию; таймаут — `Unknown`, не `Rejected` |
| `Clock` | слой времени | подтверждённое время или `None` |
| `ChainView` | ядро Fly | состояние цепи для статусов, `k_conf`, аутентифицированы ли rangeproof (без этого автоприём не включается) |
| `SlateCodec` | транспорт | текст пользователя ↔ JSON slate. Сейчас есть только `JsonCodec` (JSON как есть). Slatepack, шифрование, Nostr, Tor подключаются сюда |

| `Mailbox` | транспорт сообщений (Nostr через Tor; седьмой вызов `problem` — слова о том, что мешает, только для показа) | запечатывает текст для контакта (`seal`, без сети), публикует готовый конверт байт в байт (`publish`), отдаёт принятые и проверенные сообщения (`next_incoming`), хранит и повторяет ответ на входящее (`reply`, `resend_reply`), забывает обработанное (`done`). Поле `Ports::mailbox` необязательно: без него slate ходят вручную |

`ChainView::selected_tip()` — вершина, за которую ручается слой цепи; по умолчанию `None`. Без неё подпись без участия пользователя не делается.

**Слой цепи как поставщик блоков** — трейт `ChainFeed` из `chain-port` (`Bridge::set_chain_feed`). Кошелёк называет позицию (высоту и хеш заголовка), слой отвечает одним шагом: «ничего нового», блок ровно над позицией, шаг назад, новая точка отсчёта — либо «неизвестно». Реализация через отдельный процесс — `chain-pipe` (см. `chain-pipe/README.md`); оба крейта доступны как `fly_paycore_bridge::chain_port` и `::chain_pipe`.

Разделение обязанностей с транспортом: конверт исходящего платежа хранит **ядро** (в журнале, в одном кадре с операцией) и отдаёт транспорту готовые байты; ответ на входящий платёж хранит **транспорт**, потому что приём без состояния в журнал не пишет.

Новый внешний модуль — новый трейт в `ports.rs` и поле в `Ports`; ядро при этом не меняется.

## Методы (версия API 1)

Суммы — нанограны. На входе число или десятичная строка, на выходе всегда строка (точно и на вебе). Идентификаторы и байты — hex. `slate` — текст в формате порта `SlateCodec`.

| Метод | Параметры | Результат |
|---|---|---|
| `paycore.info` | — | `api_version`, пределы, `tip_height`, `auto_receive_since` |
| `paycore.balance` | — | `spendable`, `reserved`, `immature` |
| `paycore.address` | — | `address` |
| `paycore.history` | — | `sends[]`, `incoming[]`. В каждой записи `sends[]` есть `invoice`: `true` — это оплата счёта, её транзакцию завершает и отправляет в сеть тот, кто выставил счёт (K139); `locked`: `true` — операция подготовлена и заблокирована после обнаруженного отката (K142); `deliver_to` — ключ контакта, которому ушёл S1, или `null`, если платёж передаётся вручную (K143) |
| `paycore.slate.read` | `slate` | `stage` (`S1`…`I3`, `unknown`), `slate_id`, `amount`, `fee`, `ttl_cutoff_height`, `sender_address`, `receiver_address`: что slate говорит о себе — для окна, где человек решает (K119). Ничего не подписывает и не записывает; сумма и комиссия — слова другой стороны. Ноль не называется: `null` (ответ получателя их не повторяет) |

| `paycore.send.finalize` | `op`, `slate` (S2) | `tx`, `slate` (S3), `excess`, `payment_proof` |

С `release_locked: true` — и только для такой операции — резерв снимается по явному слову пользователя, состояние `released`, не `cancelled` (K142) |
| `paycore.send.status` | `op` | `state`, `reserve`, `conflict`, `broadcasts`, `delivery` (или `null`), `reply_held` |
| `paycore.send.finalize_held` | `op` | как у `finalize`: подпись с ответом, который пришёл сам; вызывается после подтверждения пользователем |
| `paycore.chain.sync` | — | идёт за слоем цепи от позиции кошелька, не больше 64 шагов за вызов. `chain[]` — пусто, если ничего не изменилось, иначе одна запись `{applied, rolled_back, reanchored, tip_height}`; `tip_height`; `more` — шаги ещё есть; `unknown` — слой не смог ответить (это не «ничего нового»). Когда слой ответил «ничего нового» и идёт поиск давних выходов, в том же вызове читаются куски — не больше 64 и не дольше секунды; тогда в `chain[]` добавляется запись `{search: …}` с тем же, что отвечает `paycore.search.status`, а `more` говорит, что куски ещё есть |
| `paycore.search.start` | — | начать поиск давних выходов с первого куска (спецификация, 7.19); ответ как у `status` |
| `paycore.search.status` | — | `state`: `none` — поиска не было, `reading`, `done`; для двух последних `next` (номер следующего куска или `null`), `pieces`, `found` — сколько выходов поиск добавил, `gone` — сколько выходов кошелька он нашёл потраченными |
| `paycore.wallet.chain_status` | — | Состояние применённой кошельком вершины. `at_tip` требует совпадения высоты и хеша с выбором сети в одном снимке. |
| `paycore.chain.status` | — | против чего ядро решает прямо сейчас: `state` (`at_tip`, `behind`, `unknown`), `k_conf`, `rangeproofs_authenticated`, `selected_height`, `confirmed_time`, `tip_height` кошелька |
| `paycore.delivery.pump` | необязательно `now` | `published[]` (`op`, `delivery`), `waiting`: публикует до 16 конвертов, ещё не принятых релеем |

**Паузы между публикациями.** Конверт, который релей не принял, предлагается снова не сразу: через 2 секунды, затем вдвое дольше, до 5 минут (`PUBLISH_RETRY_FIRST`, `PUBLISH_RETRY_MAX`; хост может сменить их `Bridge::set_publish_retry`). Помеха до релея — транспорт занят или ещё не готов — повторяется через первую паузу, сколько бы конверт ни ждал. `{"now": true}` — пользователь попросил: предложить все ждущие конверты сейчас. Паузы живут в памяти, в журнал не пишутся и на платёж не влияют; новый транспорт начинает без пауз. Ждущие паузу конверты входят в `waiting`.

| `paycore.delivery.ack` | `id` | — : входящее сообщение больше не нужно |
| `paycore.send.review` | `op` | Сумма, комиссия и ключ получателя из своей подготовленной операции. При отсутствии адреса в S1 возвращается `null`. Ещё `slate_id` и `slate` — сохранённый текст S1 как он был выдан: чтобы платёж, переданный вручную, можно было продолжить или передать заново из любого окна (K143). |
| `paycore.send.result` | `op` | как у `finalize`, без подписи |
| `paycore.send.broadcast` | `op` | `outcome`: `accepted` / `rejected` / `unknown` |
| `paycore.receive.draft` | `slate` (S1) | `slate` (S2) |
| `paycore.receive.auto` | `slate`, `min_amount?` | `slate` (S2) |
| `paycore.receive.set_auto` | `on` | `auto_receive_since` |
| `paycore.receive.status` | `slate_id` | `status`, `status_rule`, `known`, `spent`, `reserve`, `conflict` |
| `paycore.receive.abandon` | `slate_id` | — |
| `paycore.receive.expire` | — | `closed`. Закрывает черновики приёма старше 7 суток подтверждённого времени. Рабочий поток профиля вызывает это сам в каждом круге (K144) |
| `paycore.invoice.issue` | `amount` | `slate_id`, `slate` (I1) |
| `paycore.invoice.finalize` | `slate_id`, `slate` (I2) | как у `send.finalize` |
| `paycore.invoice.review` | `slate` (I1) | Что возьмёт оплата по счёту кошелька: `slate_id`, `amount`, `fee` (комиссия входов, которые были бы потрачены сейчас), `ttl_cutoff_height` (0 — без срока), `paid_op` (`null` или операция, которой этот счёт уже оплачен, — тогда числа прежние). Только читает: ничего не резервирует, не подписывает и не записывает; отказывает во всём, в чём до подписи отказала бы оплата (K138) |
| `paycore.invoice.pay` | `slate` (I1), `max_amount`, необязательно `max_fee` | `op`, `slate` (I2). `max_amount` и `max_fee` — то, с чем согласился пользователь: если счёт просит больше или комиссия выбранных в момент оплаты входов выше `max_fee`, ничего не подписывается (`refused`). Без `max_fee` держится только сумма. Тот же I1 повторно — прежний I2, без второй подписи |

Состояния отправки: `prepared`, `cancelled`, `released` (резерв заблокированной после отката операции снят пользователем; подпись могла существовать), `unknown`, `finalized`, `confirmed`, `contested`, `dead`.

Состояния доставки (`delivery`): `queued`, `waiting_relay`, `relay_accepted`, `expired`, `queue_busy`, `queue_full`. Они описывают только судьбу конверта: `relay_accepted` не значит ни «получено», ни «оплачено», и на `state` не влияет.

События `paycore.delivery.receive` (`kind`, `from`, `id` и дополнительные поля):

| `kind` | Что произошло | Что делать интерфейсу |
|---|---|---|
| `reply_held` (`op`) | пришёл ответ получателя, проверен и сохранён; ничего не подписано | показать платёж, по подтверждению — `send.finalize_held` |
| `reply_signed` (`op`) | ответ подписан без участия пользователя (только если хост включил автоподпись и вершина совпала) | `send.broadcast` |
| `unknown_outcome` (`op`) | подпись могла быть сделана, результата нет | как при `unknown_outcome` в `finalize` |
| `payment_answered` | входящий платёж принят без состояния, ответ ушёл | ничего |
| `reply_pending` | ответ на входящий платёж ещё не подтверждён релеем | вызвать `receive` позже |
| `needs_approval` (`slate`) | входящий платёж, автоприём выключен | спросить пользователя; `receive.draft` → `delivery.reply`, либо `delivery.ack` |
| `message` | текст от контакта записан в журнал (K120) | обновить переписку |
| `dropped` (`reason`) | сообщение отброшено | ничего |
| `deferred` | превышен предел на отправителя в этом вызове; сообщение осталось у транспорта | ничего |

Пределы на входящее (всё оттуда — недоверенный ввод): 16 сообщений за вызов; 4 от одного отправителя за вызов; текст до 96 КБ, проверяется до разбора; после 8 негодных сообщений отправитель не читается до нового платежа этому контакту или до открытия кошелька заново; счётчики — только в памяти, в журнал от мусора не пишется ничего.

Автоподпись включает хост вызовом `Bridge::set_auto_sign(true)`; JSON-метода для этого намеренно нет. По умолчанию выключена.

## Личность, контакты и запуск транспорта

Личность на транспорте (ключ Nostr) — отдельный случайный ключ, как в Goblin: из seed он не выводится и из seed не восстанавливается; его резервная копия — он сам в виде `nsec1…`. Личность и книга контактов лежат в журнале ядра — том же зашифрованном и защищённом от отката, что и платежи.

| Метод | Параметры | Результат |
|---|---|---|
| `paycore.identity.get` | — | `public`, `npub`, `imported`, `previous[]` либо `{"public": null}` |
| `paycore.identity.create` | `replace?` | как `get`; новая случайная личность |
| `paycore.identity.import` | `nsec`, `replace?` | как `get`; личность из резервной копии или из другого кошелька |
| `paycore.identity.export` | — | `nsec` — **секрет**: кто его прочёл, может читать и писать от имени кошелька (денег он не двигает) |
| `paycore.contacts.list` | — | `contacts[]`: `key`, `npub`, `name`, `address` |
| `paycore.contacts.set` | `key` или `npub`, `name`, `address?` | добавить контакт или сменить имя |
| `paycore.contacts.remove` | `key` | удалить контакт |
| `paycore.messages.send` | `key`, `text` | `id`, `state` (`waiting`): текст контакту, 1–2000 байт; запечатан и записан, публикует круг доставки (K121) |
| `paycore.messages.list` | `key` | `messages[]`: `id`, `dir` (`in`, `out`), `at`, `text`, `state` (`received`, `waiting`, `relay_accepted`, `expired`), старые сначала; до 100 (K122) |
| `paycore.messages.summary` | — | `conversations[]`: `key`, `count`, `last_at`, `last_dir` |
| `paycore.transport.status` | — | `identity`, `running`, `error` |
| `paycore.transport.restart` | — | `running`, `error` |
| `paycore.onion.status` | — | `phase` (`none`, `starting`, `up`, `listening`, `failed`), `problem`, `min_amount`, `sends[]` (`op`, `state`: `posted` или `failed`, `reason`), `asks[]` (`id`, `slate`, `slate_id`, `amount`, `claimed_sender`, `known_sender`, `left_secs`): Tor для адреса кошелька, отправки на адрес и платежи, ждущие слова пользователя (7.25) |
| `paycore.onion.send` | `op` | `op`, `state: "posted"`: отправить подготовленный платёж, названный адресом, onion-сервису этого адреса (K151). Ничего не подписывает. Ошибки: `no_onion`, `refused` с причиной |
| `paycore.onion.pump` | — | `onion[]` — события (`reply_held`, `reply_signed`, `tor_failed`, `needs_approval`, `payment_answered`, `ask_expired`, `dropped`, `asked_version`). Вызывается рабочим потоком в каждом круге |
| `paycore.onion.accept` | `id` | `slate`, `slate_id`: пользователь согласился принять ждущий платёж; ответ подписывается и уходит отправителю в ждущее соединение (K154). После срока — `refused`, ничего не подписано |
| `paycore.onion.decline` | `id` | — : пользователь отказал; отправителю уходит отказ |

Правила ядра:

- платёж с `deliver_to` возможен только контакту и только при наличии личности; проверка стоит до построения slate и до обращения к транспорту;
- пока доставленный платёж ждёт ответа, личность нельзя сменить, а его контакта — удалить;
- ключ контакта должен быть точкой кривой; своим ключом и ключом контакта одновременно один ключ быть не может;
- контактов не больше 64, имя до 64 байт без управляющих символов;
- прежние открытые ключи личности запоминаются (до 16).

**Запуск транспорта.** Хост один раз даёт мосту «фабрику» — `Bridge::set_mailbox_factory`. Мост вызывает её сразу и затем при каждой смене личности или набора контактов, передавая `TransportSpec`: секрет личности и её открытый ключ (транспорт сверяет пару до старта), ключ хранилища транспорта (выводится из секрета личности) и ключи контактов. Прежний транспорт уничтожается до запуска нового. В продукте фабрика дополняет это адресом релея, каталогом данных и сроками и запускает процесс `fly-mailbox`: `pipe::PipeMailbox::spawn` ждёт готовности транспорта, `spawn_begin` возвращается сразу и отдаёт `Starting`, у которого готовность спрашивают (`poll`). Хост (`paycore/host`) пользуется вторым способом: открытие профиля не ждёт сеть, а упавший транспорт запускается заново. Если фабрика вернула ошибку, транспорта нет, а причина видна в `paycore.transport.status`.

## Slatepack

`Bridge::set_slatepack(true)` — slate пересекают прокладку как текст Slatepack (`BEGINSLATEPACK. … ENDSLATEPACK.`), который читают и пишут другие кошельки Grin; порт `SlateCodec` при этом не используется. Входящий текст может быть открытым или зашифрованным для адреса этого кошелька; зашифрованный для другого адреса — отказ `codec`. Исходящий текст открытый: приватность даёт канал. Транспорт сообщений его шифрует; при ручной передаче текст виден всякому, кто его увидит. Шифрование для адреса получателя есть в ядре (`Core::slatepack_encode_for`), методом JSON пока не выведено. Предел текста — 64 КБ, проверяется до разбора.

## Один обработчик на профиль

`runner::Runner` — единственный поток, которому принадлежит `Bridge` открытого профиля. Хост запускает его при разблокировке и останавливает при блокировке или смене профиля.

```rust
let runner = Runner::start(
    move || open_profile(..),            // выполняется на потоке обработчика: ключи живут только там
    Duration::from_secs(2),              // пауза между кругами доставки
    Box::new(move |note| ui.push(note)), // уведомления paycore.event, не должны блокировать
)?;
let reply = runner.call(request_json)?;   // из любого потока; запросы идут по одному
runner.stop();                            // возвращается, когда потока уже нет
```

- Пока `chain.sync` отвечает `more` (у слоя цепи есть ещё блоки или куски давних выходов сверх взятого за круг), следующий круг начинается через 200 мс, а не через обычную паузу; запросы интерфейса обслуживаются между кругами (спецификация, K69).
- Круг — `chain.sync`, затем `delivery.pump` и `delivery.receive` — обработчик делает сам; интерфейс получает события уведомлениями `{"method":"paycore.event","params":{"source":"chain"|"published"|"events","event":{…}}}`. Цепь идёт первой: то, что публикуется и принимается дальше, судится по самому свежему проверенному состоянию.
- Обработчик ничего не подписывает сам, если хост не включил автоподпись при открытии.
- `stop` (или `lock_now` через общую ссылку, или удаление `Runner`) дожидается текущего запроса, новых не начинает и возвращается после завершения потока: мост, ядро, ключи журнала и транспорт к этому моменту уничтожены. Ждущие запросы получают `Stopped`.
- Второй обработчик на тот же каталог кошелька не запустится, пока жив первый: каталог заблокирован.
- Очередь запросов ограничена 64; сверх этого — `Busy`.
- Ограничение: память `ExtKeychain` из Grin при уничтожении не затирается самим типом (затирается только `BlindingFactor`); ключи журнала и стража затираются.

## Ошибки

`error.code` — число, `error.data.kind` — устойчивое имя, `error.data.reason` — английская причина для журнала. Интерфейс переводит по `kind`.

| Код | `kind` | Смысл |
|---|---|---|
| −32010 | `bad_slate` | slate не разобран или не прошёл проверку |
| −32011 | `refused` | правило ядра запрещает это сейчас |
| −32012 | `not_found` | нет такой операции или черновика |
| −32013 | `conflict` | для операции уже выбран другой ответ |
| −32014 | `unknown_outcome` | **выбран ответ, результата нет: подпись могла быть сделана, повторно не подписывается** |
| −32015 | `insufficient_funds` | не хватает средств |
| −32020…−32024 | `storage`, `storage_open`, `corrupt`, `rng`, `build` | сбой хранилища или сборки |
| −32030 | `codec` | порт `SlateCodec` не принял текст |
| −32031 | `no_mailbox` | у хоста нет транспорта сообщений |
| −32032 | `no_chain` | у хоста нет слоя цепи |
| −32602, −32601, −32600, −32700 | стандартные JSON-RPC | параметры, метод, запрос, разбор |

`unknown_outcome` интерфейс показывает отдельным состоянием, а не обычной ошибкой с кнопкой «повторить».

## Как подключить к сервису

1. После разблокировки хранилища сервис строит `ExtKeychain` из seed и открывает `Core` (`create` в первый раз, `open` далее) — образец в `examples/host.rs`, запускается: `cargo run --example host`.
2. Реализует четыре порта своими слоями и создаёт `Bridge`.
3. В обработчике `/rpc` запросы с методом `paycore.*` передаёт в `bridge.call(текст)` и возвращает ответ как есть. `Bridge` не потокобезопасен намеренно: один кошелёк — один поток или мьютекс.
4. Слой цепи при каждом проверенном блоке вызывает `bridge.core_mut().chain_advance`, при реорге — `chain_rollback`.
5. Во Flutter: `flutter/paycore_api.dart` положить в `lib/backend/`, дать ему функцию, отправляющую объект запроса на `/rpc`.

Другой транспорт (dart:ffi, канал платформы) — та же `call`: строка туда, строка обратно.

## Тесты

`cargo test --features stub` — 26 тестов: 3 в `tests/bridge.rs`, 5 в `tests/chain.rs` (цепь в памяти; три из них — поиск давних выходов), 12 в `tests/delivery.rs` (два кошелька, между их почтовыми ящиками — подставной релей) и 6 в `tests/runner.rs` (обработчик профиля на настоящих файлах; один из них запускает два подставных процесса транспорта и потому требует возможности `stub`).

## Чего нет

- Сборки прокладки вместе с настоящим транспортом в одном процессе: адаптер `Mailbox` поверх Nostr есть (`transport/mailbox-nostr`) и испытан на локальном релее, но у ядра и у транспорта разные наборы закреплённых зависимостей, и общий хост ещё не собирался.

- `flutter/paycore_api.dart` **не компилировался и не запускался**: Dart SDK в среде сборки не было.
- В сам `grinsight-service` прокладка не встроена: его код я не менял.
- `SlateCodec` для Slatepack не написан — только JSON.
- Сборки под Windows и Android, как и у остального ядра.
- Методов для seed, пароля, создания и открытия кошелька нет намеренно.
