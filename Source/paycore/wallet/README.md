# Платёжное ядро: отправка, приём, invoice, late-lock, статусы (`fly-paycore-wallet`)

Реализация разделов 6–9 и 12 спецификации (ред. 0.6) платёжного ядра поверх `fly-paycore-store` (Э1) и `fly-paycore-keys` (Э2). Slate строится типами Grin из `vendor/grin-wallet-upstream` (с применённым патчем #844), криптография — из `vendor/grin`. Ожидаемое место — `paycore/wallet`.

## Устройство

Любое изменение состояния — событие. Событие сначала пишется в журнал и только потом применяется к памяти единственной функцией `State::apply`; открытие кошелька проигрывает те же события той же функцией. Наружу (S1, S2, подписанная транзакция) отдаётся только то, чей кадр устойчив и покрыт стражем. Функция подписи отправителя одна и принимает квитанцию `Sealed` устойчивого события «выбран S2» — без неё не вызывается.

## Что сделано

- **Отправка**: резерв входов и путь сдачи в одном кадре с операцией; S1; проверка S2 без доступа к nonce (форма, тождество сделки, частичная подпись получателя); одна подпись; локальная проверка транзакции перед выдачей; отмена только до выбора S2; повтор того же S2 возвращает сохранённый результат, другой S2 — отказ; «выбран S2, результата нет» — исход неизвестен, повторной подписи нет.
- **Чужая трата входа**: операция становится оспоренной; повторить оплату можно только замещающей отправкой с общим входом либо с явным подтверждением «это не повтор»; реорг возвращает резерв тем же событием; на глубине 720 блоков операция мертва и входы свободны.
- **Приём с черновиком**: запись, высота R и путь ветки устойчивы до выдачи S2; тот же S1 — те же байты S2; предел 16, срок 7 суток по подтверждённому времени; автоматическая привязка выхода по правилам Уровня 5.
- **Приём без состояния**: ни одного кадра; включается отдельно и только при аутентифицированных rangeproof; фиксируется высота, с которой полнота держится на скане.
- **Payment proof при приёме** в обоих режимах; запрос на чужой адрес не подписывается.
- **Payment proof при отправке** (`send_prepare_with_proof`): подпись получателя проверяется до нашей подписи; снятый, поддельный proof и proof с изменённым адресом не взводят операцию; proof хранится с результатом.
- **Попытки отправки в сеть** (`send_broadcast_result`, `broadcast_attempts`): принято, отклонено, исход неизвестен; повтор — те же байты, без подписи.
- **Invoice**: `invoice_issue` / `invoice_finalize` — мы выставляем счёт, подпись получателя только по квитанции устойчивого кадра «выбран I2»; `invoice_pay` — мы платим, подпись и I2 строятся в памяти и отдаются только после устойчивого кадра с резервом; предел суммы задаёт вызывающий; тот же I1 возвращает тот же I2.
- **Late-lock** (`send_prepare_late`): S1 без резерва; входы, сдача и путь сдачи записываются одним кадром с выбором S2, до подписи; комиссия фиксируется в S1, при её нехватке или отсутствии средств — отказ без подписи.
- **Проверка миграции с v0.1** (`migrate::inspect`): база libwallet только читается; отказ со списком причин при незавершённых операциях, иначе сумма, которую обязан найти скан, и история без ключей.
- **Половина контрагента проверяется до взведения** (найдено fuzz-тестом): rangeproof каждого его выхода, вид выходов и входов, и равенство `выходы − входы + сумма·H − offset·G = его открытый excess`. Раньше S2 с верной подписью, но испорченным proof или offset взводил операцию, сборка падала, и операция навсегда оставалась «исход неизвестен» с удержанным резервом. То же для I2.
- **Offset не в hex** отклоняется до разбора: собственный разборщик Grin на таком slate паникует (`BlindingFactor::from_hex`, `unwrap`).
- **Экспорт трасс** (`trace`, `observe_send`, `observe_incoming`): сценарии в конверте `grinsight.wallet.trace.v1`; ядро заполняет только поля, которые решает само (`status`, `status_rule`, `known`, `spent`, `reserve`, `conflict`); сравнение с шагом модели — только по ним. Две трассы лежат в `traces/`.
- **Статусы**: строки S1, S2, S3, S4, S6, S7, S7a, S8 таблицы Уровня 5; баланс по категориям.
- **V в том же кадре**: изменения проверенного состояния V передаются непрозрачными байтами и пишутся одним кадром с фактами блока; снимок V — одним шагом с состоянием кошелька.
- После обнаруженного отката все прежние операции заблокированы для подписи, резервы сохраняются, новая ветка.

**Проверка самих тестов.** Одиннадцать намеренных поломок кода — каждая роняет тесты: подпись заблокированной операции; повторная подпись при повторе S2; незамеченная чужая трата; резерв не учитывается; привязка без непрерывности; подпись proof на чужой адрес; S2 не проверяется до выбора; реорг не снимает конфликт; черновик отвечает на другой S1; смерть операции через 10 блоков; приём без состояния без включения. Ещё двенадцать — для новых функций: оплата счёта сверх согласованной суммы; повтор оплаты для другого I1; I2 без устойчивого кадра; второй I2; proof без проверки подписи; proof без сравнения адресов; запрошенный proof можно снять; миграция не видит заблокированные выходы; миграция не видит открытый приём; late-lock с комиссией, которой не хватает; late-lock берёт вход из чужого резерва; входы late-lock не попадают в контекст подписи. И четыре — для проверки половины контрагента: проверка не вызывается; rangeproof не проверяется; равенство excess не проверяется; offset не проверяется на hex.

## Отступления от спецификации и упрощения

1. Кадры и снимок кодируются JSON, а не двоичным форматом; состояние копируется при каждой записи. Это вопрос скорости и объёма, не правил.
2. Зависимость — весь `grin_wallet_libwallet`; тонкий крейт slate без LMDB (В11) не выделен.
3. Отпечаток S1/S2 — SHA-256 точных байтов; формат исполнителя (В10) не подключён.
4. Контекст подписи логически закрывается при финализации и отмене, но физически остаётся в старых кадрах до второй свёртки.
5. Откат ниже снимка V отклоняется: загрузка предыдущего поколения не реализована.
6. Комиссия late-lock оценивается по выходам на момент S1 и не пересогласуется; замещающая отправка в late-lock и с proof не реализована.
7. `invoice_pay` принимает I1 с любым идентификатором: счёт с изменённым UUID — другой счёт, и он получает свой резерв. Согласие пользователя на каждый счёт — дело вызывающего слоя.
8. `migrate::inspect` только проверяет и считает; новый журнал и сверку после скана делает вызывающий слой.

## Чего нет

- Самого V: индекс выходов, bitmap, пики и их проверка остаются в ядре Fly; здесь только место для них в журнале (этап Э6 выполнен со стороны журнала).
- Строки S5; сведения минимума с Т4 и I11′ — это делает вызывающий слой.
- Воспроизведения трасс модели исследователя: её действия (`network`, `clock_on`, `quorum`, `new_snapshot`, заявка) относятся к ядру Fly, а номера строк её таблицы статусов не сверены с Уровнем 5 — нужна согласованная схема (отчёт исследователя, п. 5). Экспорт и сравнение по своим полям есть, дифференциальный прогон против модели не выполнялся.
- Сборки на Windows и Android, стража DPAPI / Keystore, испытаний на настоящей сети.
- Независимого ревью: код никто, кроме автора, не читал.
