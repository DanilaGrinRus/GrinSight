# План: режим «проверяемый лёгкий кошелёк» (Unity) для компьютера и телефона

Дата: 2026-11-10. Статус: план, RESEARCH. Опирается на результаты `GAP_EXPERIMENT_2026-11-10_RU.md`.

## 1. Что это за режим

Кошелёк Grin, который не доверяет ноде. Он сам проверяет цепочку заголовков от закреплённого checkpoint, восстанавливает множество непотраченных outputs по сегментам PIBD обычных пиров, сверяет его с `output_root` заголовка и дальше применяет каждый блок с проверкой корня. Состояние (около 100 МБ на Floonet) хранится локально и обновляется инкрементально.

Это не SPV с мегабайтами данных и не полная нода с 6 ГБ. Это третий режим: **средний по ресурсам, строгий по доверию**. Для компьютера он естественен (ресурсы не проблема). Для телефона принят бюджет **до 500 МБ на диске** и первый запуск по Wi-Fi; при таком бюджете телефон получает тот же полный режим, что и компьютер, а не урезанный.

| | Полная нода | Текущие лёгкие кошельки Grin | Unity-режим |
|---|---|---|---|
| Диск | ~6 ГБ (Floonet) | ~0 | ~100–200 МБ |
| Первый запуск | часы | секунды | ~15 мин, 250 МБ |
| Повседневно | непрерывно | секунды | секунды + 0,2 с/блок |
| Доверие к ноде | нет | полное (баланс со слов ноды) | нет для состояния UTXO; доверие к checkpoint и выбору вершины |

## 2. Архитектура: один модуль, три слоя

Цель — один исходник, который встраивается и в Rust-кошелёк (`grin-wallet`), и в C++ реализацию (Grin++), и в мобильное приложение. Для этого модуль делится на слои с чёткими границами.

```
┌──────────────────────────────────────────────────────────────┐
│  Слой 3. Хост-интеграции                                      │
│  grin-wallet: impl NodeClient   │  Grin++: адаптер к C ABI    │
│  mobile (Kotlin/Swift): FFI     │  CLI unity.py (есть)        │
├──────────────────────────────────────────────────────────────┤
│  Слой 2. Транспорт (заменяемый)                               │
│  Rust: grin_p2p (есть)  │  C++: хост отдаёт байты сегментов   │
│  и блоков через callback; модуль сети не касается             │
├──────────────────────────────────────────────────────────────┤
│  Слой 1. Ядро `unity-state` (чистое, без сети, без диска)     │
│  заголовки → проверка (есть в header-sync)                    │
│  сегменты → OutputState (есть в gap.rs)                        │
│  блок → apply + проверка output_root (есть)                    │
│  save/load с самопроверкой по заголовку (есть)                 │
│  C ABI поверх всего этого (нужно сделать)                      │
└──────────────────────────────────────────────────────────────┘
```

Принцип: **ядро не знает, откуда пришли байты**. Rust-хост подаёт их из `grin_p2p`, C++-хост — из своего P2P-стека (у Grin++ он есть), мобильный — из любого. Так одна и та же проверка обслуживает все реализации, и аудировать нужно одно ядро.

### 2.1 Что уже есть и что переезжает

| Сейчас (прототип в header-sync) | Куда в модуле |
|---|---|
| `Verifier`, `validate_and_append`, `compare_peer_chains` (main.rs) | `unity-state::headers` |
| `OutputState`, `from_segments`, `apply_body`, `save/load`, pruned set (gap.rs) | `unity-state::utxo` |
| `fetch_blocks`, `fetch_segments`, `Conn`, rate-limit (gap.rs) | `unity-net` (Rust-транспорт, отдельный крейт) |
| `unity.py` политика: пины, свежесть, два пира, статус | `unity-state::policy` + остаётся CLI |
| `rust-v2` C ABI (пример стиля: `#[no_mangle] extern "C"`, коды 0/1/-1) | образец для `unity-state` C ABI |

Ядро собирается как `rlib` + `staticlib` + `cdylib` (как сейчас `rust-v2`), зависит только от `grin_core`, `grin_chain` (для `BitmapAccumulator`, `Segment`) и `croaring`. Зависимость от `grin_p2p` уходит в `unity-net`.

### 2.2 C ABI ядра (эскиз)

Все функции возвращают код: `0` ок, `>0` вердикт, `<0` ошибка; буферы передаёт хост; память модуля освобождается парными `*_free`.

```c
// Заголовки: хост подаёт сырые заголовки, модуль проверяет PoW/difficulty/MMR.
int us_headers_open(const uint8_t* checkpoint_rwm, size_t n, us_headers** out);
int us_headers_append(us_headers*, const uint8_t* header, size_t n);        // 0 ok, <0 reject
int us_headers_tip(const us_headers*, uint8_t out_header[4096], size_t* n);

// Состояние UTXO.
int us_state_from_segments(const uint8_t* archive_header, size_t n,
                           const us_bytes* bitmap_segments, size_t nb,
                           const us_bytes* output_segments, size_t no, us_state** out);
int us_state_load(const uint8_t* file, size_t n, us_state** out, uint8_t out_header[4096], size_t* hn);
int us_state_save(const us_state*, const uint8_t* header, size_t hn, uint8_t** out, size_t* n);
int us_state_apply_block(us_state*, const uint8_t* block, size_t n,
                         const uint8_t* header, size_t hn);                 // 0 ok, <0 root mismatch
int us_state_lookup(const us_state*, const uint8_t commit[33], uint64_t* pos, uint8_t* features);
int us_state_iter_utxo(const us_state*, uint64_t from_pos, uint64_t max,
                       us_utxo* out, size_t* n);                           // для скана кошелька
uint64_t us_state_height(const us_state*);  uint64_t us_state_utxo_count(const us_state*);

// Политика (чтобы хосты не расходились в правилах).
int us_policy_check(const us_headers*, const us_state*, uint64_t now_unix,
                    const us_policy_params*, us_policy_result* out);
```

Что хост обязан делать сам: сеть, выбор пиров, хранение файлов, часы. Что хосту запрещено: трогать состояние в обход модуля.

## 3. Встраивание в grin-wallet (Rust)

Точка встраивания — трейт `NodeClient` в `libwallet/src/types.rs` (проверено по текущему `master`, коммит `f097811e`, 2026-10-11). Кошелёк вызывает его из `owner.rs`, `scan.rs`, `tx.rs`, `updater.rs` и не знает, стоит за ним HTTP-нода или что-то ещё. Делается `UnityNodeClient: NodeClient`, выбирается в конфиге кошелька (`node_client = "unity"` вместо URL).

| Метод `NodeClient` | Как обслуживается в Unity-режиме | Статус |
|---|---|---|
| `get_chain_tip` | вершина проверенной сессии заголовков (height, hash) | есть |
| `get_outputs_from_node(commits)` | поиск в локальном состоянии: (commit, height, mmr_index). Высота известна только для outputs, созданных после checkpoint (по `output_mmr_size` заголовков); для старых отдаётся высота checkpoint как нижняя граница, что влияет лишь на число подтверждений | есть, нужна карта pos→height |
| `height_range_to_pmmr_indices` | из заголовков: `output_mmr_size` на границах диапазона | тривиально |
| `get_outputs_by_pmmr_index` | обход локального UTXO по позициям; **rangeproofs в состоянии нет**, нужны сегменты rangeproof PMMR для диапазона (PIBD отдаёт их так же, как output-сегменты) | нужно: загрузка rangeproof-сегментов по запросу, ~675 байт на UTXO |
| `get_kernel(excess)` | подтверждение исходящей транзакции. Вариант А: скан kernels в блоках промежутка (блоки мы и так качаем); вариант Б: kernel-сегменты по высоте. Для кернелов старше checkpoint — только Б | нужно |
| `post_tx` | рассылка через `grin_p2p` (`Peer::send_transaction`) нескольким пирам; подтверждение — через `get_kernel` | нужно, просто |
| `get_version_info` | версия модуля + версия заголовка из вершины | тривиально |
| `node_url`/`api_secret` | не используются; возвращать заглушку | тривиально |

Полный восстановительный скан (`scan.rs`) идёт через `get_outputs_by_pmmr_index` по всему UTXO с rangeproofs. Это одноразово ~2 ГБ на Floonet (столько же тянет и обычный restore через ноду). Повседневный `updater.rs` использует только `get_outputs_from_node` по известным commitments, что состояние отдаёт за микросекунды.

## 4. Встраивание в Grin++ (C++)

Grin++ содержит свою ноду с P2P-стеком, PIBD и свой кошелёк; его кошелёк тоже ходит к ноде через внутренний интерфейс (высота, outputs по PMMR-индексу, рассылка транзакции). План:

1. Собрать `unity-state` как `staticlib` (`.lib`/`.a`) с заголовком `unity_state.h`, как уже делает `rust-v2` для C ABI.
2. Написать адаптер `UnityNodeClient` (C++), реализующий тот же внутренний интерфейс, что и клиент локальной ноды Grin++, поверх C ABI. Сеть — P2P-стек Grin++: он уже умеет запрашивать заголовки, блоки и PIBD-сегменты; адаптер передаёт сырые байты в модуль.
3. Режим включается флагом конфигурации: вместо запуска полной ноды поднимается только P2P-слой и Unity-состояние.

Что нужно проверить на старте этапа: имена и сигнатуры внутреннего интерфейса Grin++ в его текущей версии (здесь не сверялись), возможность запустить P2P без полной ноды.

**Grin++ как источник данных для Unity (сверено по исходникам 2026-11-10).**
- Оригинальный GrinPlusPlus (коммит `fb9a13b`): заголовки (до 512 за ответ) и блоки (`GetBlock`, тела хранятся неделю — 10 080 блоков) отдаёт; все PIBD-запросы игнорирует («PIBD handling not yet implemented»), PIBD в рукопожатии не объявляет.
- Форк `DanilaGrinRus/GrinPlusPlus-BearTry-contrib`, ветка `Main` (`ba8f237`): отдача сегментов реализована (высоты как в Grin 5.5.2: bitmap 9–13, output 11–15, rangeproof 7–11, kernel 9–13; архивная высота по той же формуле; лимит 500 запросов/мин на соединение, 2000/мин на узел), но архивная отдача выключена по умолчанию (`GRINPP_PIBD_ARCHIVE_SERVING=1`) и **жёстко запрещена на mainnet** (`IsServingAllowed = optIn && !isMainnet`) до приёмки G-09. Без архива отдаются только сегменты текущего (вершинного) состояния — для Unity бесполезно.
- Следствие: на mainnet сейчас Grin++ даёт Unity только заголовки и блоки; сегменты — от Rust-узлов. Включение архивной отдачи в Grin++ — отдельная задача (вне Unity); Floonet с opt-in — хороший тест совместимости двух реализаций.

## 5. Компьютер и телефон: один код, две политики

| | Компьютер | Телефон |
|---|---|---|
| Работа | фоновый сервис (`unity-service`): держит 4–8 соединений, применяет блоки по мере прихода, состояние всегда на вершине | по запросу при открытии кошелька: догнать вершину, показать баланс; фоновые обновления по расписанию ОС |
| Пиры | много, разные /16, выбор вершины по работе; хранить и ротировать список | 2–3 пира из сохранённого списка, добор при расхождении |
| Диск | состояние + 2 снимка + блоки последних суток для быстрого reorg | бюджет 500 МБ: состояние + 1 снимок; Floonet ~210 МБ, mainnet измерено 55 МБ на снимок (~110 МБ с двумя) |
| Первый запуск | 15 мин; можно параллелить сегменты по пирам | 15 мин на Wi-Fi; показывать прогресс; разрешить отложить; без Wi-Fi спрашивать |
| Часы | системные | системные + сверка с медианой времени пиров |
| Rangeproofs для restore | скачать все один раз (Floonet ~2 ГБ, mainnet измерено 550 МБ), на диске не хранить | то же, по Wi-Fi; на mainnet ~550 МБ разово — терпимо только по Wi-Fi; альтернатива — restore с компьютера |

Общая политика (свежесть вершины, минимум пиров, fail-closed) задаётся параметрами `us_policy_params`, а не кодом хоста, чтобы телефон и компьютер не разошлись в правилах.

## 5.1 Чекпоинт: три уровня доверия

Пользовательский продукт должен уметь строить чекпоинт сам — тем же кодом, что `run_mainnet.ps1` (синк с генезиса с проверкой PoW, сложности и MMR заголовков, затем подтверждение хеша другими узлами). Вопрос только в цене для пользователя.

**Цена чекпоинта с генезиса на mainnet** (высота ~4,1 млн):
- трафик ≈ 1,9 ГБ (расчёт: ~455 байт на заголовок Cuckatoo32, без накладных расходов протокола; живой замер — в итогах прогона);
- время: с близкого быстрого узла ~27 мин при лимите 300 запросов заголовков в минуту (без лимита узел отдавал ~100 тыс. заголовков за 30 с, но отключал клиента); с далёкого публичного узла ~100 тыс. за 5 мин → 3+ часа;
- память и диск: хранятся только 32-байтные дайджесты и хвост последних заголовков; процессор — не узкое место.

**Уровни:**

| Уровень | Как | Для кого | Защищает от | Не защищает от |
|---|---|---|---|---|
| 1. Встроенный + сверка (по умолчанию) | чекпоинт в релизе (подписанный, этап 4); при первом запуске сверка полей заголовка с ≥2 публичными API и обозревателем и подтверждение хеша ≥2 узлами из разных сетей | все; телефон — старт за минуты | подмены одного источника | сговора издателя релиза со всеми источниками |
| 2. «Проверить с генезиса» | пользователь строит чекпоинт сам: полный синк заголовков с одного-двух узлов + подтверждение хеша вершины ещё ≥2 узлами (`--confirm-peer`) + та же сверка с API | компьютер — кнопка в настройках; телефон — только Wi-Fi + зарядка | доверия к издателю чекпоинта | eclipse: все узлы у одного злоумышленника (но ему придётся честно намайнить работу всей подставной цепочки) |
| 3. Скользящий | после 1 или 2 клиент сам двигает свой чекпоинт вперёд по проверенной цепочке (состояние и хвост заголовков уже сохраняются) | все | повторной работы с генезиса | — |

**Как часто обновлять чекпоинт (схема без доказательств по MMR):**

Нижняя граница свежести: чекпоинт должен лежать ниже архивной высоты PIBD — не ближе 4320 блоков (~3 дня) к вершине, выровнен на 720.

Цена устаревания — заголовки от чекпоинта до вершины (~455 байт на блок, 1440 блоков в сутки; скорости из прогона 2026-11-10: быстрый узел ~150 тыс. заголовков/мин при ≤300 запросах/мин, медленный публичный ~20 тыс./мин):

| Возраст | Заголовков | Трафик | Быстрый узел | Медленный узел |
|---|---|---|---|---|
| 3 дня | 4,3 тыс. | ~2 МБ | секунды | секунды |
| 1 месяц | 43 тыс. | ~20 МБ | ~20 с | ~2 мин |
| 6 месяцев | 260 тыс. | ~120 МБ | ~2 мин | ~13 мин |
| 1 год | 525 тыс. | ~240 МБ | ~3,5 мин | ~26 мин |

Главный эффект устаревания — не трафик, а запас для атаки при eclipse: подставную цепочку строят от чекпоинта, а быстро снизить сложность (WTEMA) можно только большими промежутками меток времени, которые не могут уйти дальше «сейчас + 5 мин» (лимит будущих меток времени по умолчанию: `DEFAULT_FUTURE_TIME_LIMIT` = 300 с в Grin, настраивается `future_time_limit`; в Grin++ — `5 * BLOCK_TIME_SEC`). Чем старше чекпоинт, тем больше у атакующего «бюджета времени», чтобы уронить сложность и дёшево намайнить подделку; с чекпоинтом в ~3 дня нужно честно выдать ~3 дня работы почти на текущей сложности.

Правила:
- **Встроенный чекпоинт** — в каждом релизе, не реже раза в 1–3 месяца. Старше ~6 месяцев — предупреждение и обязательная сверка с публичными источниками (как `checkpoint_crosscheck.py`), а не молчаливое принятие.
- **Скользящий чекпоинт на устройстве** — после каждой успешной проверенной синхронизации переносить на высоту `floor((tip − 4320) / 720) · 720`; предыдущий хранить запасным. Пользователь, открывающий кошелёк раз в неделю, всегда имеет чекпоинт моложе ~10 дней.
- **Проверка работы против eclipse** — накопленная работа от чекпоинта до вершины сравнивается с ожидаемой (сложность чекпоинта × число блоков, соответствующее прошедшему времени по часам устройства, с допуском). Работа в разы меньше ожидаемой — цепочка подозрительна, даже если все пиры согласны: fail-closed и сверка с публичными источниками.

**Требования к уровню 2 (новое по итогам mainnet-прогона 2026-11-10):**
- докачка: сохранять дайджесты и прогресс, продолжать после обрыва и перезапуска (сейчас синк начинается с нуля);
- параллельная загрузка по диапазонам с нескольких узлов: один медленный узел не должен определять время;
- ограничение частоты: ≤300 запросов/мин на узел (лимит Grin — 500 сообщений/мин, при превышении узел банит); молчание узла ниже целевой высоты — ошибка, а не «конец цепочки»;
- разнообразие узлов: соседние подсети (например, `103.11.76.x` и `103.11.77.x`) считать одним источником; узлы, к которым уже подключена своя нода пользователя, не принимают второе соединение с того же IP — брать известные, но не подключённые;
- подтверждение хеша вершины дешевле второго полного синка: один запрос заголовков с локатором = наш хеш; если ответ начинается с высоты +1 и ссылается на наш хеш, цепочка узла содержит наш заголовок, а значит и всю историю под ним.

**Исследовательское направление (не готово):** в каждом заголовке Grin есть `prev_root` — корень MMR всех предыдущих заголовков. В принципе это позволяет проверять случайную выборку из сотен заголовков с доказательствами по MMR вместо всех 4 млн (идея FlyClient): мегабайты вместо гигабайт. Препятствия: в P2P-протоколе Grin нет сообщений, отдающих такие доказательства; выборка должна быть взвешена по работе, а MMR Grin по работе не взвешен (нужны дополнительные запросы через `total_difficulty` в заголовках). Это отдельный этап исследования и, вероятно, расширения протокола. Подробно — отдельный документ `HEADER_MMR_PROOFS_PROPOSAL_RU.md`: в ветке `staging` Grin уже есть PIHD (сегменты по 512 заголовков по индексу, бит 0x80) — основа для параллельного синка уровня 2; предлагаемое дополнение — сообщения с доказательствами по MMR заголовков без изменения консенсуса.

## 6. Этапы и критерии приёмки

Оценки в неделях ориентировочные, для одного разработчика, без аудита.

| # | Этап | Критерий приёмки | Оценка |

## 7. Риски

- **Eclipse/Sybil** не устраняются количеством IP. Подписанные checkpoint переносят доверие на издателя. Нужно честно описать модель доверия пользователю.
- **Объём состояния на mainnet — измерен, риск снят** (прогон 2026-11-10, см. `GAP_EXPERIMENT_2026-11-10_RU.md`): UTXO 350 620, файл состояния **55,0 МБ** (≈110 МБ с двумя снимками — вчетверо ниже бюджета телефона); сегменты архива при первом запуске **117,6 МБ**; rangeproof-скан для restore **549,7 МБ** (оценка 240 МБ была занижена — сегменты несут данные по всем 9,38 млн позициям MMR); блоки промежутка ~3,4 тыс. Первый запуск (restore по фразе) со встроенным чекпоинтом, без локальной ноды: ≈ 27 мин с одного узла; ≈ 11 мин с общей очередью по 4 узлам; **≈ 4 мин (236–257 с)** при параллельной установке на 7–8 узлах — одно соединение на узел, блоки, сегменты и rangeproof одновременно, сегменты выходов высоты 13. Обычное открытие — десятки секунд. Предел задаёт лимит 500 сообщений/мин на узел (≈8 750 запросов); подробности — `GAP_EXPERIMENT_2026-11-10_RU.md`, раздел «пользовательский сценарий». С синком с генезиса +28 мин.
- **Rangeproofs для restore** — 2 ГБ разового трафика, на диск не пишутся (проверяются потоково). Для телефона допустимо по Wi-Fi; запасной путь — restore с компьютера.
- **Лимит 500 сообщений/мин** у узлов Grin ограничивает скорость первого запуска (измерено: ≈4 мин на 7–8 узлах — близко к пределу). Узел держит одно соединение с одного IP и помнит закрытое до 20 с: одно соединение на узел на всю установку, список узлов между запусками.
- **Зрелость coinbase и NRD** требуют высоты и кернелов: из состояния UTXO не выводятся, нужны заголовки и kernel-сегменты.
- **Grin++**: внутренний интерфейс может отличаться от ожидаемого; этап 8 начинать со сверки исходников. На mainnet Grin++ сейчас не отдаёт PIBD-сегменты (см. §4): источником сегментов остаются Rust-узлы.
- **Первый синк с генезиса** дорог (≈1,9 ГБ, от ~30 мин до 3+ ч в зависимости от узлов) и чувствителен к банам за частоту запросов — см. §5.1.
