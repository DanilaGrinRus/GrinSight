## Как это стыкуется с ядром

Ядро видит транспорт через порт `Mailbox` (`paycore/mailbox`, шесть вызовов). Соответствие:

| Вызов порта | Что стоит за ним |
|---|---|
| `seal(контакт, текст)` | `seal_payment` → `envelope()` |
| `publish(конверт)` | сессия с этим контактом → `publish_envelope` со сроком, который ядро хранит рядом с конвертом |
| `next_incoming()` | `receive_pending` по сессиям контактов; сообщение повторяется, пока не подтверждено |
| `done(id)` | `acknowledge_received` |
| `reply(id, текст)`, `resend_reply(id)` | `seal_payment` → запись в `ReplyStore` → `publish_envelope`; повтор — из `ReplyStore` |

## Адаптер `mailbox-nostr`

`NostrMailbox` реализует порт для одного открытого профиля и живёт на потоке его обработчика.

- **Сессии.** По одной на контакт, открываются при первой надобности; при сбое соединения сессия закрывается, следующая попытка — через 5 секунд. Не больше 64 контактов. Способ соединения задаёт `Connector`: в продукте `TorConnector` (общий клиент Tor и адрес релея), в тестах — соединение с локальным релеем.
- **Запечатывание** — только для контактов из списка, одними ключами, без сети.
- **Публикация** — адресат читается из самого конверта, сессия проверяет подпись, размер и срок и отправляет те же байты. Ответ честный: «принято» только по подтверждению релея; закрытое окно доставки — «срок истёк»; всё остальное — «неизвестно».
- **Приём.** Сообщение контакта отдаётся ядру повторно в каждом круге, пока ядро не скажет «обработано». Сообщения не от контактов и обычный текст ядру не передаются.
- **Ответы** (`store::ReplyStore`). Ответ на входящий платёж запечатывается один раз, сначала записывается на диск, потом публикуется; повтор и перезапуск отправляют сохранённый ответ. Файл на каждый ответ, зашифрован XChaCha20-Poly1305 ключом, который даёт хост; имя файла не раскрывает сообщение; существующий ответ не заменяется; не больше 512; при старте удаляются ответы с закрытым окном доставки. Нечитаемый ответ новым не заменяется.
- Порт синхронный, транспорт асинхронный: у почтового ящика своя среда исполнения tokio, вызывать его можно только с обычного потока.

**Отдельный процесс.** По решению 21.11 транспорт работает отдельным процессом `fly-mailbox` (`src/bin/fly-mailbox.rs`): в процессе с ключами кошелька нет сетевого кода, а процесс с Tor и Nostr не видит ни одного ключа кошелька. Процесс кошелька запускает его без аргументов и с пустым окружением и говорит с ним через стандартный ввод и вывод кадрами `paycore/mailbox-pipe`. Первым кадром приходит всё, что нужно для старта: ключ транспортной личности, ключ хранилища ответов, адрес релея, каталог данных, контакты и сроки. Дальше — шесть вызовов порта, пока ввод не закрыт. В стандартный вывод идёт только протокол; журнала процесс не ведёт. Закрытие ввода (блокировка профиля) завершает процесс.

Каталог данных должен существовать, быть задан полным путём и не быть каталогом кошелька: в нём состояние Tor и подкаталог `replies`.

Чего ещё не хватает до работы в приложении — это уже хост (этап 3, продолжение):

- откуда хост берёт ключ транспортной личности, список контактов, адрес релея и ключ хранилища ответов при открытии профиля;
- проверка на живом релее через Tor. Сам Tor в этом процессе поднимается: тест `live_the_process_brings_up_tor_and_seals` (по умолчанию пропускается, запуск — `run-live-tor-test.ps1`) прошёл на Windows 21.11 — Tor за 11 секунд при пустом окружении процесса, публикация на несуществующий релей — «неизвестно»;
- приём от неизвестных отправителей (`UnsolicitedInbox`) к порту не подключён: слышны только контакты.

Файловая очередь исследователя (`queue_store`) адаптером не используется: исходящие хранит журнал ядра, ответы — `ReplyStore`.
