# Процесс цепи (`fly-chain`): заголовки от встроенной точки, состояние на архивной точке, блоки до вершины, давние выходы

Шаги 5.2–5.5 этапа 5. Процесс кошелька не содержит сетевого кода; за цепью следит отдельный процесс, который кошелёк запускает и с которым говорит по каналу (`paycore/chain-pipe/README.md`). Здесь четыре крейта:

| Крейт | Что в нём |
|---|---|
| `chain/headers` (`fly-chain-headers`) | проверка цепи заголовков от стартовой точки, без сети и без ввода-вывода, кроме одного файла |
| `chain/state` (`fly-chain-state`) | состояние цепи на архивной точке ноды, собранное из сегментов и сверенное с заголовком, и его продвижение блоками; без сети, два файла |
| `chain/fly-chain` | программа: соединения с нодами Grin, загрузка заголовков, сегментов состояния, блоков и rangeproof давних выходов, ответы кошельку |
| `chain/tips` (`fly-chain-tips`) | вопрос публичным нодам названных операторов о вершине, по HTTPS; кворум, подтверждённое время и заявки о большем из их ответов; признаки, по которым спрашивать (шаг 5.7); программа спрашивает через него с ред. 0.32 |
| `chain/tor` (`fly-chain-tor`) | клиент Tor (Arti 0.48) для отправки транзакций и мост: обычное TCP-соединение на 127.0.0.1, переданное потоку через Tor |

**Что умеет эта версия.** Соединяется с нодами сетевым кодом самой ноды (`grin_p2p`), проверяет каждый заголовок от стартовой точки до вершины, хранит проверенную цепь в файле, после перезапуска перепроверяет файл и продолжает, переходит на ветвь с большей работой. Затем собирает у нод состояние на их архивной точке — непотраченные выходы и концы трёх деревьев, по которым обязуется заголовок, — и сверяет каждый кусок с проверенным заголовком. Дальше применяет к этому состоянию блоки до вершины, сверяя каждый с проверенным заголовком, и отвечает кошельку из применённых блоков: следующий блок, шаг назад, новая опора. Кошельку, который спрашивает, отдаёт давние выходы — rangeproof всего непотраченного старше блоков, кусками, каждый сверен с проверенным заголовком. **Чего не умеет:** отправлять транзакции, выбирать среди источников — выбранной вершины она не называет, поэтому статусы в кошельке остаются предварительными.

## Стартовая точка

Проверять цепь от генезиса лёгкому кошельку не по силам, поэтому он начинает с заголовка S, за который кто-то ручается. Запись точки (`chain/headers/points/*.json`, формат версии 1 записи `CheckpointRecord` ядра Fly) несёт: сам S, два заголовка перед ним и доказательство, из которого восстанавливаются пики MMR заголовков.

Проверка записи (`checkpoint::check`) сводит всё к одному хешу:

- два предыдущих заголовка названы по хешу, от S вниз;
- S следует из них по всем правилам;
- пики восстановлены из доказательства для S−1 под корнем, который записан в самом S;
- то, что запись говорит о результате (пики, размер MMR, суммарная работа), должно с ним совпасть.

После этого на веру принимается только одно: что хеш S — правильный. Этого проверка заменить не может.

**Три вида точки (ред. 0.34, спецификация 7.22).** Точка разработки — снята с ноды во время разработки, за неё никто не ручается; всё выбранное на ней — «условно». Точка выпуска — сделана командой `point` из проверенной цепи, и при этом её заголовок назвали публичные ноды двух операторов в разных сетях, а другой не назвал никто; ручается автор сборки. Своя точка — файл `own-point.json` в каталоге данных; ручается пользователь. На точке выпуска и на своей «условно» нет. Программа называет вид точки всякий раз, когда говорит о ней.

**Вшитая точка — два файла:** запись `chain/headers/points/main.json` (`test.json`) и происхождение `main.origin.json` (`test.origin.json`) — вид, сеть, высота и хеш, когда сделана, откуда заголовки, кто подтвердил. Точкой выпуска считается только та, чьё происхождение называет вид `release`, ровно этот заголовок и ноды двух разных операторов в двух разных сетях; иначе — точка разработки (`origin::Origin::vouches_for`). С ред. 0.35 вшиты точки выпуска: Mainnet 4 115 520 (`000622ed…761482`, назвали Grincoin.org, Grinffindor, Grin.money, Raubritter, Grin Coffee) и Testnet 3 345 840 (`767c501e…775883`, назвали Grinffindor и Grin.money). Прежние точки разработки (Mainnet 4 113 930, Floonet 3 331 315) остались в `points/` под старыми именами — на них опираются тесты.

**Как сделать точку.** `fly-chain point --network main|test --data <каталог> --kind release|own --out <каталог> [--height N]` (на Windows — `make-point.ps1`). Программа догоняет заголовки, берёт архивную точку сети (или `--height`, не выше; и не ниже трёх заголовков над своей точкой), строит запись из проверенной цепи (`HeaderChain::record_at`; запись принимается, только если проверка читает её обратно до того же заголовка) и спрашивает каждую ноду списка операторов о заголовке на этой высоте (`get_header`). Хоть одна назвала другой — ничего не пишется. Для `release` нужны совпадения двух операторов в разных сетях; пишутся `<сеть>.json` и `<сеть>.origin.json` — их кладут в `chain/headers/points/` и собирают заново. Для `own` пишется `own-point.json` — в каталог данных кошелька.

**Своя точка.** Есть `own-point.json` в каталоге данных — программа начинает с него. Не проходит проверку или от другой сети — программа не запускается и говорит почему; вшитая вместо неё не берётся.

**Смена точки.** Файл заголовков другой точки той же сети уступает место: новая цепь строится рядом (`headers.next`), заголовки старого файла выше новой точки проверяются от неё и сохраняются, пока следуют; затем новый файл встаёт на место старого. В выводе — строка `replaced: …`. Файл другой сети не трогается.

## Правила для одного заголовка

`rules::check_step` — те же проверки, что делает нода (`grin_chain::pipe::validate_header` и разбор недоверенного заголовка в `grin_core`), теми же функциями `grin_core`: версия для высоты, время строго растёт, счётчики выходов и кернелов растут, вес блока в пределах, доказательство работы, работа оплачена доказательством, прирост суммарной работы равен сложности по правилу. Три оговорки:

- поддерживаются только заголовки после четвёртого хардфорка (точка всегда позже; прежнее правило сложности требует часа предыдущих заголовков);
- обязательство по предыдущим заголовкам (`prev_root`) проверяет тот, кто держит пики, — `chain::State::step`;
- «не из будущего» — отдельный вопрос: заголовок, чьё время впереди часов больше допуска ноды, не отклоняется, а откладывается.

Неизвестная версия заголовка — отказ: за цепью, которая сменила правила, программа не идёт.

## Файл заголовков

`<каталог данных>/headers.dat`: 49 байт начала (метка, сеть, высота и хеш точки), дальше заголовки подряд. Файлу не верят: при каждом открытии каждый заголовок проверяется заново от точки, и файл обрезается на первом, который не следует. Оборванная запись, мусор в конце, изменённый байт, чужой заголовок — всё это просто укорачивает цепь, и недостающее скачивается снова. Файл другой точки или другой сети не используется и не трогается. Второй процесс тот же файл открыть не может.

## Ветви

Предложенные заголовки проверяются до записи. Ветвь, уходящая от цепи на более раннем заголовке, проверяется от него и заменяет конец цепи, только когда несёт **больше суммарной работы**; при равной работе остаётся первая. До тех пор ветвь ждёт в памяти. Решает работа, не длина. Ветвь, которая уходит глубже 1440 заголовков, не принимается, о ней сообщается.

## Ноды

- Адреса — из `--chain-peer` хоста; если их нет, спрашиваются имена-сиды сети (список из исходников ноды).
- Соединения **прямые, не через Tor**: ноды видят адрес компьютера как адрес обычного пира Grin. Ничего о кошельке в этих соединениях нет — программа скачивает все заголовки подряд. Транзакции кошелька с ред. 0.36 по ним не идут: они уходят через Tor (ниже).
- Держится до трёх соединений. Спрашивают того, кто заявляет больше работы, чем проверено. Заявление решает только, кого спросить; фактом оно не становится.
- Нода, приславшая заголовок, которого не может быть ни в одной верной цепи, оставляется до конца запуска. Верные заголовки перед ним сохраняются.
- Нода, чей ответ ничего не добавил, отдыхает (30 секунд, вдвое дольше каждый раз, до 10 минут).
- Программа ничего не раздаёт: на любой запрос данных — ошибка.

## Состояние на архивной точке (шаг 5.3)

**Зачем.** Чтобы отдать кошельку блок как проверенный (шаг 5.4), содержимое блока надо сверить с заголовком, а заголовок обязуется по состоянию *после* блока: по корням деревьев выходов, rangeproof и кернелов и по корню накопителя bitmap непотраченных выходов. Пересчитать эти корни можно, только зная состояние *до* блока. Нода отдаёт состояние сегментами (PIBD) и только на одном заголовке — своей **архивной точке** A: `вершина − 2880` блоков, округлённая вниз до кратного 720 (на Mainnet это от двух до двух с половиной суток назад; меняется раз в 12 часов).

**Что собирается** (`chain/state`, `archive::Collector`):

| Часть | Из чего | Зачем |
|---|---|---|
| bitmap непотраченных выходов | все сегменты дерева bitmap | корень накопителя после каждого блока; потрачен ли выход |
| непотраченные выходы с позициями | все сегменты дерева выходов | найти вход блока; пики дерева выходов |
| пики дерева выходов | те же сегменты | добавлять выходы блоков |
| пики дерева rangeproof | один последний сегмент и его доказательство | добавлять rangeproof блоков |
| пики дерева кернелов | один последний сегмент и его доказательство | добавлять кернелы блоков |

Сами rangeproof непотраченных выходов и история кернелов для проверки блоков не нужны и не скачиваются (rangeproof понадобятся на шаге 5.5).

**Проверка — как у ноды.** Каждый сегмент проверяется кодом самой ноды (`Segment::validate`, `validate_with`) под корнем из заголовка A, а заголовок A берётся из проверенной цепи заголовков, не от ноды, которая шлёт сегменты. Корень дерева выходов нода заявляет сама; к заголовку его привязывает хеш вместе с корнем накопителя.

**Читается только то, что проверено.** Нода, не уплотнявшая свои файлы, кладёт в сегмент все листья и все промежуточные хеши; проверка ноды из них читает только нужное: данные листа, если непотрачен он или его сосед, и один хеш на каждый участок без непотраченных выходов — хеш наибольшего такого поддерева. Остальное в сегменте проверкой не покрыто, и там может стоять что угодно. Сборщик читает ровно те же куски, что прочла проверка, и никакие другие; в файл пишет тоже только их. Тест меняет в сегменте по одному куску каждого вида: либо сегмент отвергнут, либо кусок никем не прочитан и получается то же состояние.

**Файл** `<каталог данных>/state.dat`: 48 байт начала (метка, высота и хеш архивного заголовка), дальше записи «вид, длина, сегмент». Файлу не верят: при каждом открытии каждый сегмент заново проходит через сборщик — проверка под заголовком, потом чтение, — как если бы пришёл от ноды. Что не прошло, и всё после него, отрезается и запрашивается снова. Файл, который не является файлом состояния, не трогается; файл состояния на другом заголовке не трогается, пока не известно, что собирать вместо него.

**Сбор по сети** (`chain/fly-chain`, `schedule` и `state`):

- запросы идут только к нодам, которые объявили, что отдают состояние сегментами; если все места (пока состояние собирается, их восемь) заняты нодами, которые его не отдают, через 30 секунд одна из них оставляется ради другой;
- нода на запрос либо отвечает, либо молчит — ответа «у меня нет» не бывает; поэтому у запроса срок 20 секунд, неотвеченный кусок уходит к другой ноде, три неотвеченных подряд — нода оставляется (на время);
- одной ноде — не больше четырёх запросов сразу и не чаще одного в четверть секунды: нода считает сообщения и сама выставляет слишком разговорчивого пира;
- сегменты дерева выходов запрашиваются на 24 вперёд; пришедший раньше очереди проверяется под заголовком сразу (эта проверка от порядка не зависит) и ждёт очереди;
- нода, чей сегмент не прошёл проверку, оставляется до конца запуска; верное, что она прислала раньше, остаётся;
- сегмент, который у ноды не спрашивали, или для другого заголовка, не рассматривается; нода, которая шлёт такие подряд (больше 16), оставляется.

**Архивная точка сдвигается.** Нода отвечает только за ту архивную точку, которая у неё сейчас. Если сбор не закончен, а цепь ушла за следующую границу, собранное на прежней точке закончить нельзя: сбор начинается заново на новой. Законченное состояние сохраняется, куда бы сеть ни ушла: от него вперёд пойдут блоки (шаг 5.4).

**Архивная точка ниже стартовой.** Состояние можно собрать только на заголовке, который есть в проверенной цепи, то есть не ниже стартовой точки. Если архивная точка сети ниже — программа говорит, через сколько блоков сбор станет возможен. Для точки выпуска это значит: она должна быть старше примерно двух с половиной суток к первому запуску, иначе первый запуск ждёт.

**Живые сети, 22.11** (`run-live-state-test.ps1`, три ноды по сидам): Mainnet — архивная точка 4 114 800, 4 612 сегментов за 470 с, 353 500 непотраченных выходов, файл 61 МБ, перезапуск перепроверяет всё за 2,8 с; Floonet — 1 697 сегментов за 224 с, 2 972 629 выходов, файл 129 МБ. Первый же перезапуск на Floonet показал ошибку: от сегмента внутри уплотнённого поддерева длиннее сегмента в файле не оставалось ничего, и файл обрывался на нём при каждом открытии. Исправлено; что остаётся от сегмента для файла, теперь перед записью само проходит проверку ноды.

**Крупные сегменты выходов (ред. 0.24, 23.11).** Ноды режут дерево выходов на сегменты высоты 11 (2 048 листьев), но на запрос отдают и более крупные, до высоты 15 (32 768 листьев): проба `fly-chain segments` на двух нодах Mainnet (`live-segments-test-20261122-2300.log`). Программа запрашивает дерево выходов сегментами высоты 15: проверка та же, под тем же корнем, запросов в шестнадцать раз меньше. Высота выбирается до первого принятого сегмента выходов и потом не меняется. Если запрос крупного сегмента не отвечен в срок, а ни одного крупного ещё не пришло ни от кого, сбор переходит на высоту 11, и молчание по снятым запросам никому не засчитывается; если хоть один крупный пришёл, высота остаётся. Файл состояния помнит высоту своих сегментов. Окно крупных сегментов — 16. В итоговой строке `collected:` два счётчика: `check_ms` (проверка сегментов, пришедших раньше очереди) и `take_ms` (приём сегментов). **Mainnet, 22.11 23:34** (`run-live-state-test.ps1 -Network main`, с ключом `-Fresh` — с пустого места): 307 сегментов, состояние собрано через 72,1 с и 66,7 с после запуска (в них 12 с заголовков) вместо 195,5 с; перехода на мелкие не было.

## Блоки после архивной точки (шаг 5.4)

`chain/state`, модули `advance` и `blocks`; в программе — модуль `follow`. Из состояния до блока и содержимого блока считаются корни трёх деревьев и bitmap и сверяются с заголовком из проверенной цепи; заголовок, приехавший с блоком, должен совпасть с проверенным побайтно (хеш заголовка в Grin — хеш одного доказательства работы, по хешу сравнивать нельзя). Корни говорят, что это тот блок, о котором заголовок, но не что блок верен: это проверка блока кодом ноды (вес, порядок, суммы, rangeproof, подписи кернелов), она идёт один раз, когда блок пришёл. Блоки снимаются назад по одному до архивной точки. Блоки лежат в `blocks.dat`; при каждом открытии они применяются заново под проверенными заголовками, и файл обрывается на первом, который не сходится — в том числе когда цепь заголовков сменила ветвь, пока программа не работала.

Не проверяется: что выходы, непотраченные на архивной точке, сходятся по сумме с кернелами до неё (истории кернелов нет); зрелость coinbase-выхода, когда неизвестно, где кончаются зрелые (сразу после архивной точки при близкой стартовой точке).

**Загрузка.** Блоки запрашиваются по хешу проверенного заголовка, на 16 вперёд, с теми же пределами и сроками, что сегменты. Пришедший раньше очереди ждёт — но только под самим проверенным заголовком. Нода, приславшая под проверенным заголовком не тот или негодный блок, оставляется до конца запуска. Когда цепь заголовков перешла на другую ветвь, блоки прежней снимаются.

**Кошельку** (порт `chain-port`): без позиции и с позицией ниже архивной точки — новая опора на архивной точке; блок над позицией — выходы с rangeproof и позициями в дереве выходов (считая с нуля), commitments входов, excess кернелов; хеш не из цепи — шаг назад на один блок; позиция выше применённого — «неизвестно»; «ничего нового» — только когда применённые блоки дошли до вершины цепи заголовков и ни одна подключённая нода не заявляет больше работы. Оценка «у вершины» — при том же условии; выбранной вершины нет.

Тесты (5, на цепи кода ноды): блоки 211–236 по одному, каждый проходит проверку ноды и даёт корни заголовка; отмена до любой высоты и обратно — то же состояние; отказы — не следующий блок, заголовок с тем же хешем и другим содержимым, чужое содержимое под проверенным заголовком, вход на несуществующий и на уже потраченный выход, вход дважды, пропущенный и лишний вход, изменённые выход, rangeproof и кернел, выход с занятым commitment, незрелый coinbase; блок с завышенной наградой и безупречным заголовком отвергнут проверкой ноды, а по одним корням прошёл бы; файл блоков — перезапуск, отмена вместе с файлом, оборванный конец, изменённый байт, лишний байт, сменившаяся цепь заголовков, чужой файл. Двадцать семь намеренных поломок, каждая роняет тесты.

**Живые сети, 22.11** (`run-live-blocks-test.ps1`): Mainnet — 2 958 блоков от 4 114 800 до 4 117 758 за 306 с, Floonet — 3 321 блок за 616 с; ни одного отвергнутого блока. ## Давние выходы (шаг 5.5)

Блоки начинаются с архивной точки. Кошелёк, восстановленный из фразы, находит то, чем фраза владела раньше, одним способом: пробует свои ключи на rangeproof всего непотраченного. Собранное состояние rangeproof не держит; программа докачивает их, когда кошелёк спрашивает, и не хранит. Правила — спецификация, 7.19 (K59–K67).

`chain/state`: `rangeproofs_of(сегмент, заголовок, bitmap)` — rangeproof непотраченных выходов одного сегмента дерева rangeproof: сегмент проходит проверку кода ноды против корня в заголовке с bitmap непотраченных на этом заголовке, наружу идут только листья, которые проверка прочла. `Live::bitmap_at(высота)` — bitmap, каким он был после блока на этой высоте: к нынешнему возвращается потраченное позже и убирается созданное позже. `Live::unspent_between(первая, последняя)` — непотраченные выходы с позициями в этих пределах.

`chain/fly-chain`, модуль `old`. Кусок для кошелька — сегмент дерева rangeproof (высота 11, 2 048 листьев) на той архивной точке, которую ноды отдают сейчас; на вопрос о прежней точке нода молчит. Пришедший сегмент проверяется, к каждому rangeproof по позиции берутся commitment и признак coinbase из состояния; выходы, потраченные после архивной точки, отбрасываются. Когда кошелёк спрашивает кусок, отдаются те из удержанных выходов, что непотрачены после последнего применённого блока; этот блок назван в ответе (`at`), а `before` — высота архивной точки сегмента. Куска нет — «неизвестно», и он запрашивается к следующему вопросу.

Запросы идут, только пока кошелёк спрашивает (последний вопрос не старше минуты), на 32 куска вперёд, с теми же пределами и сроками, что сегменты состояния. Пока нода не ответила на этой архивной точке, у неё спрошен один кусок: первый запрос заставляет ноду строить состояние на точке, и это бывает дольше срока ответа. На диск ничего не пишется. Прочитанное кошельком отпускается; когда кошелёк замолчал — отпускается всё. Когда блоки сняты, удержанное выбрасывается целиком: в куске нет выходов, потраченных на ушедшей ветви, а на другой они могут быть живы. Когда ноды перешли на следующую архивную точку, запросы к прежней забываются без счёта молчаний; удержанное остаётся — rangeproof выхода на любой более поздней точке тот же. Нода, приславшая rangeproof, которые не сходятся с проверенным заголовком, оставляется до конца запуска.

Объём: 675 байт на каждый непотраченный выход сети. **Живые сети, 22.11.** `fly-chain old` на Mainnet (`live-old-test-20261122-1734.log`): 4 592 куска, 350 226 выходов, 236 МБ rangeproof за 389 с с трёх нод, ни одного отвергнутого сегмента. Под хостом с фразой пользователя (`run-live-restore-test.ps1`): Mainnet — найдено 2 выхода, 6,251 GRIN, с пустого диска всё вместе за 20 минут 45 секунд; Floonet — 1 688 кусков (около 2 ГБ), 4 выхода, 1 372,557499 GRIN за 48 минут; суммы сошлись с известными пользователю.

**После K68, вечер 22.11** (`run-live-old-test.ps1 -Network main -Fresh`, `live-old-test-20261122-1850.log`): Mainnet с пустого диска — всё вместе 480 с: заголовки и состояние к 182,5 с, блоки к 330,4 с, давние выходы 147,9 с (около 31 куска в секунду вместо 12), одновременно до восьми нод. Под хостом с фразой — 666 с вместо 1 245 с (`live-restore-test-20261122-1906.log`), а после правки правила K69 на стороне кошелька (спецификация ред. 0.22) — 518 с, поиск 175 с (`…-2026.log`); те же 2 выхода и 6,251 GRIN.

**Сколько нод.** Обычно программа держит три ноды. Пока качать много — собирается состояние, блоки отстают от вершины заголовков больше чем на окно загрузки, кошелёк читает давние выходы — до восьми (спецификация, K68): каждую ноду спрашивают не чаще прежнего, нод больше. Подключённые ради этого потом не отключаются, но ушедшие сверх трёх не заменяются. Добавлено после живых прогонов: и сбор состояния, и блоки, и давние выходы шли ровно со скоростью, которую дают три ноды при четырёх запросах в секунду к каждой. На живой сети с восемью ещё не прогонялось.

Тесты: один новый и дополнение к тесту отмены в `chain/state` (rangeproof непотраченных на архивной точке — ровно они и каждый с тем доказательством, что в блоке; изменённый rangeproof, сегмент другой высоты, сегмент, которого нет, лист чужого сегмента; bitmap прежних высот) и 8 в `chain/fly-chain` (один модульный и `tests/old.rs`: без сети на цепи из 236 блоков — куски спрашиваются, когда спрашивает кошелёк, берётся только спрошенное и сверенное, кусок говорит о нынешней вершине; снятые блоки, смена архивной точки, назойливая нода; нода, ещё не ответившая на архивной точке, спрошена об одном куске; по сети на цепи из 40 блоков, где пять выходов не тратятся никогда, — кошелёк по каналу получает ровно их, а без вопроса кошелька ничего не запрашивается; нода перешла на другую ветвь — удержанное запрошено заново; нода с изменёнными rangeproof оставлена, больше не спрошена и не подключена; `fly-chain old`).

**Поиск с места (ред. 0.24, 23.11).** Кошелёк, который шёл по блокам и пропустил их часть, называет блок, до которого знал все свои выходы (`old_outputs_since`, запрос `0x06` канала, версия канала 3). Если этот блок есть в цепи заголовков программы (высота и хеш) и не выше последнего применённого, кусок, чей участок был полон к этому блоку, отдаётся сразу и без rangeproof: всё, что в участке непотрачено сейчас, из проверенного состояния. За такими кусками программа ни к кому не обращается; rangeproof запрашиваются с первого участка, который тогда полон не был. Блок другой ветви, блок без заголовка — все куски целые. Решение принимает `old::leaves_after`, число «голых» кусков — `old::full_pieces`. На живой сети не прогонялось.

## Отправка транзакции (шаг 5.6)

Модуль `post`. Кошелёк передаёт готовую транзакцию по каналу; ответ — то, что известно в эту минуту: «принято», «отклонено» или «неизвестно». Нода на транзакцию не отвечает, поэтому программа знает только то, что видит сама (спецификация, 7.20, K71–K77).

- **До отправки** транзакция проверяется против проверенного состояния: разбор без остатка, проверка кода ноды (структура, вес, подписи, rangeproof, суммы), виды кернелов и блокировка по высоте, комиссия, входы среди непотраченных, выходов там ещё нет. Негодная «отклонена» и не уходит никуда. Без состояния у вершины или без нод — «неизвестно», ничего не отправлено.
- **Через Tor (ред. 0.36, спецификация 7.23).** Годная транзакция уходит стеблем (Dandelion) через Tor: сначала API публичной ноды из списка по HTTPS (`push_transaction`), если ни одна из двух не приняла — нода сети её сетевым кодом. Отдельный поток `send`; Tor поднимается при первой отправке, его состояние — в `tor/` каталога данных. Второй раз та же транзакция не отправляется. По своим соединениям о ней ничего не идёт — ни она, ни вопрос о ней.
- **Своя нода (ред. 0.37, K115).** Адреса из `own-nodes.txt` в каталоге данных (по одному `https://…` в строке, не больше четырёх) получают транзакцию первыми, до нод списка. О вершине их спрашивают, как ноды списка; голосом они не считаются. Негодные строки не используются, кошельку об этом говорится.
- **Причина неудачи Tor (K116)** — словами Tor («rejected by exit policy» и т. п.), без имени и адреса. `fly-chain tor` для каждой неудачной ноды сети говорит, принимает ли она соединение напрямую.
- **«Принято»** — когда нода передала нам эту транзакцию не стеблем (одну или склеенную с чужими) либо её кернелы есть в применённом блоке. Сетевой код отдаёт потоку цепи только транзакции с нашими кернелами; остальные транзакции сети выбрасываются.
- **Срок стебля** — 180 с от удачной попытки: не вернувшаяся транзакция уходит через Tor на объявление, затем раз в 300 с ещё раз, каждый раз начиная с другой ноды.
- **Если Tor не вышел** — повтор через 60 с тем же видом; кошелёк видит причину первой в тексте о состоянии. Напрямую, по своим соединениям, — только с согласия пользователя (`--chain-direct-post` у хоста): тогда стебель одной своей ноде, по сроку — объявление всем, затем вопросы по одной.
- **Поворот цепи:** транзакция из снятого блока снова не в блоке и уходит ещё раз. Расхождение ветвей ищется по следу из 128 просмотренных блоков.
- **Предел** — 16 транзакций; уступает та, что дольше всех в блоке.

Исходящие живут в памяти: после перезапуска программы кошелёк передаст транзакцию снова, и она уйдёт стеблем ещё раз. Нода, получившая стебель, знает, что он наш: чужих транзакций программа не пересылает.

Тесты: 6 в `tests/post.rs` и модульный тест следа. Три — без сети, на проверенном состоянии цепи с настоящими транзакциями (`Source::grow_paying`, `Source::paid_tx` в `chain/state`); три — по сети с двумя нодами: стебель одной ноде и один раз, «принято» после пересылки другой нодой без единого вопроса; объявление по сроку, запрос ноды по хешу кернела и подтверждение; блок и поворот цепи. Намеренных поломок — 32. На Windows проходят (`windows-tests-20261122-2132.log`). **Живая сеть, 22.11** (`run-live-payment-test.ps1 -Network test`, `live-payment-test-20261122-2229.log`): платёж 0,1 GRIN на Floonet — стебель через 1 с после подписи, «принято» через 31 с (нода вернула транзакцию из сети), в блоке через 71 с; получатель увидел деньги. Объявление по сроку стебля на живой сети не понадобилось.

**После перезапуска (ред. 0.27).** Программа не хранит отправленное между запусками: перечня транзакций кошелька на диске нет. Кошелёк передаёт транзакцию снова; если она ещё не в блоке, она уходит стеблем, как новая; если уже в цепи (все выходы непотрачены в проверенном состоянии, входов нет) — ответ «принято», ничего не отправляется (`post::in_chain`).

## Вопрос названным операторам и выбранная вершина (шаг 5.7)

Крейт `chain/tips` и модуль `accept` программы (спецификация, 7.21, K89–K102). Кто стоит между программой и сетью, тот выбирает, с какими нодами она соединится, и адреса в разных подсетях от этого не защищают. Поэтому о вершине спрашивается публичная нода оператора, известного по имени, по HTTPS под своим именем: за неё стоящий на пути ответить не может. Так требует норма Т4 (П10–П12); соединения сетевым кодом остаются свидетельством о ветви, голосом они не являются.

- **Один вопрос.** `get_tip` собственного интерфейса ноды (`/v2/foreign`), без параметров. В запросе название и версия программы и больше ничего. Одно соединение — один вопрос, от вопроса к вопросу ничего не переносится.
- **Кто отвечает.** Сертификат проверяется по удостоверяющим центрам, вшитым в программу, и только по ним. Другое имя, неизвестный центр, сертификат вне срока, не TLS — не ответ.
- **Пределы.** Заголовок 8 КиБ, тело 16 КиБ, статус только 200, вид ответа точный; всё вместе не дольше заданного срока.
- **Время.** Из строки `Date` того же ответа (решение пользователя 23.11: без Roughtime), с двумя моментами, между которыми сервер её написал.
- **Независимость.** Записана в списке при выпуске: оператор и сеть (ASN). Два источника — два голоса, только если различается и то и другое. Нода пользователя спрашивается, но независимой не считается.

Списки версии 2: Mainnet — `grincoin.org` (AS24940), `mainnet.grinffindor.org` (AS9145), `api.grin.money` (AS13335, прокси Cloudflare), `main.grin.raubritter.org` и `mainnet.grin-coffee.com` (обе AS16276, друг от друга не независимы). Testnet — `testnet.grinffindor.org` (AS9145) и `testapi.grin.money` (AS13335, прокси Cloudflare); подтвердить должны обе.

Проверить список на живой сети: `run-live-tips-test.ps1` (ключ `-Network test` для Testnet). Программа `fly-tips-check` спрашивает каждую ноду один раз и печатает ответы; скрипт дописывает сети нод. 23.11 на Mainnet ответили все пять за 0,22–0,88 с, четыре назвали одну вершину, пятая — предыдущий блок; времена разошлись на 1 с (`live-tips-test-20261123-0235.log`). Второй прогон, уже с правилами кворума и времени: вершина подтверждена, время подтверждено с шириной 1,9 с; на Testnet обе ноды назвали одну вершину (`live-tips-test-20261123-0308.log`).

**Что из ответов складывается (ред. 0.29).**

- **Место ответа** (`verdict`). Рядом с вершиной, которую программа проверила сама, слово источника — «подтверждает» (ровно её высота, хеш и работа), «отстал» (блок своей цепи ниже вершины), «впереди» (высота или работа больше) или «в стороне» (всё остальное — не ответ). Блок, которого у программы нет, не объявляется ни предком, ни соперником.
- **Поколение и кворум** (`generation`). Опрос для одной вершины, с номером и сроком. Вершина подтверждена, когда ответила половина списка, двое независимых назвали ровно её строго до срока и никто не назвал большего. Вердикт читается после каждого ответа и может упасть. Срок 45 с растёт до 300 с, только если ответы приходили после срока.
- **Заявка о большем** (`claims`). Стоит и блокирует, пока программа не проверит этот блок; через 30 минут истекает и ещё 30 минут остаётся оговоркой. Сроки идут только по подтверждённому времени.
- **Подтверждённое время** (`time`). Интервалы из ответов двух независимых источников сходятся в пределах 30 с, часы компьютера не дальше 5 минут. Держится до 6 часов и пока часы компьютера идут с ним в ногу.
- **Память** (`memory`). Номер поколения, нижняя граница времени и заявки — в одном файле; нечитаемый файл — отказ подтверждать, а не начало с нуля.
- **Опрос целиком** (`round`, `survey`). Все источники сразу, каждый в своём потоке; вызывающий идёт шагами и читает вердикт после каждого.

Отступления от нормы Т4 перечислены в спецификации (7.21). Один оператор списка может остановить подтверждения — заявив больше работы или держа неверные часы; причина должна быть показана пользователю.

**Когда спрашивать (ред. 0.31).** При старте, после долгой отлучки и по признаку (`signs`); фоновой сверки нет. Признаков пять: вершина старше 30 минут; цепь отстала от блока в минуту больше чем на 720 блоков или двадцатую часть; работа последних 1440 блоков меньше трёх пятых предыдущих; ноды меньше чем в трёх сетях (по первым 16 битам IPv4, 32 — IPv6); за последний час меньше 30 блоков. Первые четыре — с порогами приложения к норме Т4, пятый добавлен сверх неё. Признак ничего не доказывает, он заставляет спросить. ## Запуск

Кошельком — без аргументов, по каналу. Для пробы на сети:

```
fly-chain headers --network main|test --data <каталог> [--peer host:port]... [--seconds N]
fly-chain state   --network main|test --data <каталог> [--peer host:port]... [--seconds N]
fly-chain blocks  --network main|test --data <каталог> [--peer host:port]... [--seconds N]
fly-chain select  --network main|test --data <каталог> [--peer host:port]... [--seconds N]
fly-chain old     --network main|test --data <каталог> [--peer host:port]... [--seconds N]
fly-chain proofs  --network main|test --data <каталог> --peer host:port... [--rounds N] [--sample N]
fly-chain point   --network main|test --data <каталог> [--peer host:port]... --kind release|own --out <каталог> [--height N]
fly-chain tor     --network main|test --data <каталог>
```

`tor` поднимает Tor, как перед отправкой, спрашивает через Tor каждую публичную ноду о вершине и делает через Tor рукопожатие с двумя нодами сети: строки `tor: up …`, `api: … height=…`, `network: … height=… agent=…`, `summary: …`.

`old` доходит до вершины, как `blocks`, и затем сама читает давние выходы, как читал бы кошелёк, — без ключей: ход `old: piece=…/… outputs=… proof_bytes=…`, в конце `old: pieces=… outputs=… proof_bytes=… at=… before=… seconds=…`.

`headers` печатает ход и строку `synced: height=… hash=… work=…`; код выхода 0 — догнала ноды, 1 — время вышло, 3 — не смогла начать. `state` после этого идёт дальше: `state: height=… segments=… kept=…`, ход `state=сделано/всего`, в конце `collected: height=… unspent=… file_bytes=…`. `blocks` идёт до вершины: `blocks: base=… kept=…`, ход `blocks=применено/заголовков`, в конце `applied: height=… blocks=… unspent=…`. На Windows это делают `run-live-headers-test.ps1`, `run-live-state-test.ps1` и `run-live-blocks-test.ps1`.

## Проба доказательств заголовков (`proofs`)

Измерительная команда для нод с патчем mimblewimble/grin #3963; кошелёк этими сообщениями не пользуется. Патч добавляет пару сообщений: по хешу заголовка-якоря и списку высот (до 64) нода присылает заголовки этих высот и доказательства, что каждый — лист дерева заголовков под корнем, записанным в якоре. В закреплённом сетевом коде ноды есть сторона, которая отвечает, и проверка; стороны, которая спрашивает, нет, поэтому модуль `probe` ведёт соединение сам: рукопожатие кодом ноды, дальше чтение и запись сообщений напрямую.

`proofs` доводит заголовки до вершины обычным путём, берёт якорем собственный проверенный заголовок на 20 ниже вершины и с каждой названной нодой (`--peer` обязателен, имена-сиды не используются) соединяется отдельно. Нода, не объявившая возможность, не спрашивается. Вопросы: тройка соседних высот у начала заголовков версии 5; 21 тройка по истории до стартовой точки; тройка и 21 тройка из проверенных программой; тройка до четвёртого хардфорка; вопрос с неизвестным якорем. Каждый — `--rounds` раз (по умолчанию 5). В ответе проверяется: якорь и высоты те, что спрошены; каждый заголовок — лист под корнем якоря; proof of work покрывает поля заголовка; для верхнего заголовка тройки — сложность от двух предшественников; заголовки, которые программа проверила сама, равны её собственным побайтно. Строки: `anchor: …`, `node: … agent=… header_proofs=yes|no connected_ms=…`, `proofs: node=… kind=… heights=… answered=n/N bytes=… ms_min=… ms_median=… ms_max=… check_ms=… members=… pow=… full=… before_hf4=… same_as_verified=…`. Код выхода 1, если хоть один ответ отвергнут или нода не ответила.

Нода не впускает второе соединение с того же адреса сразу после закрытого первого (первое — то, которым программа качала заголовки), поэтому соединение повторяется до 90 с со строкой `not let in yet`.

**Живая сеть, 22.11** (`run-live-proofs-test.ps1 -Peer …`, собирает в отдельную папку `target-proofs`; `live-proofs-test-20261122-1908.log`): две ноды с патчем, Mainnet, все 50 ответов приняты. Три высоты — 3,2–3,4 КБ, 63 высоты — 66–71 КБ (1,0–1,1 КБ на высоту); ответ — 237–252 мс, один обмен с нодой, для 63 высот на 10 мс дольше, чем для трёх; первый вопрос о 63 давних высотах — 2,0 и 3,6 с; проверка ответа на 63 высоты — 1,2–1,6 мс. На неизвестный якорь нода молчит и следующий вопрос обслуживает. Собственная проверка патча (`verify_header_proofs_with_pow`) ответ из одних троек не принимает: предшественников требует и для нижней высоты тройки. Подробно — спецификация, раздел 16.

**Выборка (`--sample N`, в скрипте `-Sample N`).** Вместо перечисленных вопросов — N высот (от 1 до 20 000), взятых случайно и равномерно по всей истории ниже якоря, каждая с двумя предшественниками; тройки не пересекаются; запросы по 21 тройке; всем названным нодам — одни и те же высоты. Строки `sample: drawn=…` и `sample: node=… sampled=… heights=… requests=… answered=n/N bytes=… seconds=… answer_ms_median=… answer_ms_max=… check_ms_total=… members=… pow=… full=… before_hf4=… same_as_verified=…`. Это измерение цены, а не правило выборки, которому можно доверять. **Живая сеть, 22.11** (`live-proofs-test-20261122-2000.log`): 1000 высот, 48 запросов, 3 354 625 байт, все ответы приняты; 18,0 с на одной ноде (медиана ответа 345 мс) и 33,4 с на другой (632 мс); проверка всех ответов — 61 мс. Все 4,1 млн заголовков с первого блока — по оценке 1,7–2,5 часа. После прогона одна из двух нод выведена.
